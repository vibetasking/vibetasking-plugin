# Reacting to platform events

Every notable thing that happens in a workspace lands as an activity: a contact parked by a channel's waiting room, a run that failed or paused, a balance running low, a document added to Knowledge. An activity trigger turns them into runs: at most once an hour it starts one run of its agent over the activities that arrived since its last sweep and match its filters.

## Wiring it

1. Give the reacting agent an activity trigger: `create_trigger` with `agent_id`, `activity` naming the `activity_types` the agent handles, `agent_ids` naming the agents whose runs it watches when it watches only some, `severities` when only some matter, a `filter` when the lists are not narrow enough, and a `prompt` saying what to do with what arrives. The `filter` is one Jinja2 expression over the activity, the record it is about, its run and its channel, the same one webhooks take (the `vibetasking` skill's `webhooks.md` lists the fields): `activity.data.variant in ['retry', 'fix_mcp']` keeps only the failures a re-dispatch can fix. `update_trigger` replaces `activity` whole, so send the filter again with any change to it.
2. Write the agent's prompt around the events it receives: what each kind means, what to check, which tool settles it, and when to leave it to a person. The agent needs no sandbox for this. Every call in the table below is an API call, so a reaction is a few tool calls, not a build.

Each fire carries every matching activity since the last one, so a burst is one run. A trigger never fires on the reacting agent's own activity or on a rehearsal's, so an agent never reacts to what it did. Never fire an agent on `MESSAGE_INSERTED` or on the run state kinds (`RUN_QUEUED`, `RUN_EXECUTED`, `RUN_PENDING`, `RUN_CANCELED`) without a tight `agent_ids` filter, or a `filter` naming the channel and the role (`record.role == 'USER' and run.channel_id == '…'`): every message and every state change of every run would land in its fires. A system outside the platform hears the same activities through a webhook subscription (`create_webhook`), which delivers each one as it happens.

## What the agent receives

The first message is the trigger's prompt, then the fire's payload as JSON:

- `since` and `until`: the hour, or so, it covers.
- `count`: how many activities matched, of which `activities` carries the newest hundred.
- Each activity: `id`, `type` (from the table below), `severity` (`BLOCKING`, `WARNING`, `INFO` or null), `table` and `record_id` (what it is about), `surfaced_at`, and `data`, the detail listed per kind below with the `run_id` and `agent_id` it names.

An activity may have been handled since it arrived: read its state with `get_activity` before acting on it, and read the record it is about with that record's own get operation.

## What each event admits

The right hand column names the operations that settle each kind. Read a run's conversation with `list_messages` filtered by `run_id`. Close an inbox card the agent handled on its own with `acknowledge_activity`. Where a person has to finish (a payment, an OAuth grant, a document), the agent's job is to mint the URL and deliver it to the right person: `start_conversation` on a channel reaches them over WhatsApp, Telegram or email, and `send_message` reaches the owner in their own conversation.

| Event | `data` | What the agent can do | Operations |
|---|---|---|---|
| `CHANNEL_WAITING` | `channel_id`, `contact_id`, `contact_name` | Read the held messages, judge the contact against the admission rules, admit or turn away. Leave it undecided when unsure and the card stays for a person. | `settle_waiting_run` with `decision` `approve` or `reject` |
| `RUN_FAILED` with `variant` `retry`, `grow_sandbox`, `fix_mcp`, `fix_model`, `maintenance`, `wrong_environment` | `variant` | Read the trace and the cost, fix the agent when the failure is its configuration (its model, for `fix_model`), then re-dispatch. | `get_run_trace`, `get_run_costs`, `update_agent`, `send_message` |
| `RUN_FAILED` with `variant` `update_payment`, `credit_topup`, `insufficient_credits` | `variant` | A record of one run parked on the balance or the payment method, with no severity. The workspace's one `CREDITS_EXHAUSTED` or `AUTO_PURCHASE_FAILED` row is what to act on. | |
| `RUN_WAITING` with `variant` `cost_guard` or `raise_limit` | `variant` | Raise the ceiling on the agent, or on this run alone, then re-dispatch. A `raise_limit` card whose text says the run carries on by itself at 00:00 UTC stopped a daily cap, which lifts on its own then, so raise it only when the run must go on sooner. A message after a `cost_guard` card lets the run carry on past the guard. | `update_agent` or `update_run` with `config.credit_limit`, then `send_message` |
| `RUN_WAITING` with `variant` `insufficient_credits` | `variant` | As the payment variants of `RUN_FAILED`. | |
| `RUN_WAITING` with `variant` `daily_budget` | `variant` | The runs it counts against, its agent's or its preset's, spent their daily credit limit, so the run waits, before its turn or during one, and carries on by itself at midnight UTC (the card's `resets_at`). Raising the limit is a person's change, which `update_agent` with `config.daily_credit_limit` asks them for on a card, and only a member writing to the run continues it alone for the rest of the day. | `update_agent`, `send_message` |
| `RUN_INTERRUPTED` on a question | | Answer it. | `send_message` |
| `RUN_INTERRUPTED` on a human handoff | | Speak as the human with `role` `OPERATOR`, or hand the conversation back to its agent with a USER post. | `send_message` |
| `RUN_INTERRUPTED` on a connection, an asset or a secret request | | Mint the OAuth URL for the owner, link the asset, store the secret. A browser step needs a person. | `create_connection`, `quote_asset` and `create_asset`, `create_secret` |
| `RUN_BLOCKED` | `blocker`, `run_id` | Read the blocker, fix the agent, run it again. | `update_agent`, `retry_run` |
| `RUN_ANOMALOUS` | `departures`, and `running` while the run still works | The run departed from its agent's usual (its cost, its turns, its tool errors or what it answered). With `running` true it is still working, past five times its usual cost, messages or duration: read what it is doing and stop it when it should not carry on, and the card settles with the turn. Without it, a review traced the departure to the agent's side: read the run, fix the agent where its instructions led to the departure, and close the card. | `get_run_trace`, `get_run_costs`, `stop_run`, `update_agent`, `acknowledge_activity` |
| `RUN_DISLIKED` | `comment` when the person left one | A person gave the run a thumbs down. Read the run and the comment, fix the agent's prompt, or ask its owner what went wrong. | `get_run`, `list_messages`, `update_agent`, `send_message` |
| `ASSET_RENEWAL_FAILED` | `reason` `renewal_error`, `invoice_id`, `renewal_id` | A renewal could not be processed and waits on the platform's operators. Nothing is owed yet, so tell the owner and leave it. | |
| `INTEGRATION_REAUTH` | `toolkit_slug` | Mint the reconnect URL and get it to the owner. | `create_connection` with the integration's `integration_id` |
| `CHANNEL_DISCONNECTED` | `channel_type`, `reason`, plus the channel's identifiers | A revoked or removed WhatsApp grant takes a new link from `create_connection` of `type` `WHATSAPP`, and a dropped LinkedIn account one of `type` `LINKEDIN`, sent to the owner. A WhatsApp number Meta took off its Cloud API (`ACCOUNT_OFFBOARDED`) comes back on its own when it moved to a new phone and its owner left VibeTasking ticked in WhatsApp Business, else it takes that same link. A Meta restriction, violation or ban is lifted by Meta alone, and a mailbox reconnects from the app, so brief the owner on those. | `create_connection`, `send_message` |
| `ENGINE_ACCOUNT_REFUSED` | `type` and `name` on an API account, `engine` on a subscription | One of the workspace's own AI accounts was refused, its key or token revoked or expired: an API key, a cloud tenancy or its Claude Code or Codex subscription. What ran on it moves on: an `automatic` entry to VibeTasking, billed in credits, an entry naming the account to the next entry, and it stops where none is left. It holds until a person who manages the workspace's credentials sets the account again in the app's settings: tell the admins which account. | `send_message` |
| `WEBHOOK_FAILING` | | Read why in `data.last_error` or `data.last_status_code` and the subscription, then fix, disable or repoint it. | `get_webhook`, `update_webhook` |
| `EVALUATION_FAILED`, `EVALUATION_ERRORED` | `run_id` | Re-evaluate, tighten the case, or fix the prompt that failed it. | `evaluate_run` with `force`, `update_case`, `update_agent` |
| `TRIGGER_MISSED` | `reason`, `expected_at`, and by reason `last_fire`, `limit`, `detail`, `app` | Without a `reason` a schedule missed its time: fire the run it missed. An event trigger's `quiet` means its sender stopped sending since `last_fire`, so tell the owner which app to check, and `skipped` that its filter or condition has kept every event out since then, so read a recent event and fix the filter or condition with the owner. `filter_failed` names the failure in `detail`: fix the filter. `no_contact` means an event named no contact its agent's channels take: fix the trigger's contact template. `refused` means the sender sends faster than the trigger takes: tell the owner. A POLL trigger's `check_failed` asks for its integration reconnected, `page_full` for a shorter interval and `oldest_first` for an event listed newest first. | `fire_trigger`, `get_trigger`, `update_trigger`, `create_connection`, `send_message` |
| `SECRET_REDACTED` | `kinds`, `sources` | Stop the run and tell the owner which credential to rotate. | `stop_run`, `send_message` |
| `SECRET_REFUSED` | `names`, `destination`, `surface`, and `credentials` (`vault_item`, `host`) when a host on a Vault item would open it | Add the host to the credential's hosts only when its owner confirms it. | `update_vault_item` or `update_secret` with the host in `data.allowed_hosts` |
| `SECRET_REJECTED` | `name`, `vault_item`, `host`, `status`, `error`, `description` | The token endpoint at `host` refused a TOKEN item's credential: a secret that expired or was revoked, a wrong client id, a scope it does not grant. Only a person holding a working credential can fix it, so tell the item's owner which item and what the endpoint said. It resolves itself once the endpoint hands out a token again. | `send_message` |
| `BUNDLE_UPDATED` | `status`, `failure_reason` or `valid_until` | Collect what the rejection asks for from the owner, then resubmit. | `add_bundle_document`, `submit_bundle` |
| `TOLLFREE_VERIFICATION_UPDATED` | `e164`, `status`, `rejection_reasons` | Resubmit the verification with the corrected answers. | `submit_tollfree_verification` |
| `STRIPE_ACCOUNT_UPDATED` | `charges_enabled`, `disabled_reason`, `currently_due` | Mint the onboarding link and get it to the owner. | `create_stripe_onboarding_link` |
| `STRIPE_DISPUTE_CREATED` | `dispute_id`, `amount`, `reason`, `evidence_due_by` | Read the dispute and brief the owner before the deadline. Evidence is submitted by a person in Stripe. | `list_stripe_disputes` |
| `AGENT_UNOWNED` | `profile_id`, `name` | The agent's author left the workspace, so its runs start without an owner and reach nothing a member owns. Who owns it next is a person's call: brief the admins with the agent's name. | `send_message` |
| `SUPERVISOR_STALLED` | `reason`, `overdue` | A supervisor stopped handling its agents' inbox items, which now reach their people. On `overdue`, on autonomous alone, it let items pass their deadline: list them, answer or close each, and it counts again. On `unseated` nobody seated owns it, as when the person it acts for left or support started it: an admin claims the run or gives it to a member. | `list_activities` with `holder_id` and `inbox`, `acknowledge_activity`, `update_run` with `profile_id` |
| `SUPPORT_ACCESSED` | `email` | VibeTasking staff opened a support session, which the workspace's support access setting allows: one activity per session, with no severity. Nothing to do unless the owner did not expect it: they switch support access off in the workspace's People settings. | none |
| `WORKSPACE_HALTED` | `via`, `reason`, `run_id` | An owner or an admin stopped every agent of the workspace, `profile_id` naming who. Nothing of it runs until a person resumes it, a run reacting to this event included, so it reaches a run of another workspace alone. Resuming is a person's call: brief them with who halted it and why. | `resume_workspace`, which waits for a person's approval |
| `WORKSPACE_RESUMED` | `via` | A person let the workspace's agents run again, `profile_id` naming who. Its conversations answer what waited, and runs the halt stopped stay stopped until someone writes to them. | none |
| `AGENT_BUDGET_SPENT` | `spent`, `limit`, `date`, `runs` | The agent, or for runs with no agent the preset (`table_name` `presets`), spent its daily credit limit, so its runs wait, each on its own card, until midnight UTC. Raising an agent's limit is the owner's change, which `update_agent` with `config.daily_credit_limit` asks them for. It resolves once every run it names works again. | `update_agent`, `send_message` |
| `PERMISSION_REQUESTED` | `requests`, each with `request_id`, `kind`, `tool_name`, `requester` and the `run_id` that asked, null for a direct call | Another person's agent asked to make a call through a resource you manage, or to have a component shared, and its run went on. The answer is its owner's: pass the request on to them, never answer it on your own judgement. | `list_permission_requests` |
| `PERMISSION_ANSWERED` | `request_id`, `kind`, `tool_name`, `approved`, `remembered`, `answered_by`, `expires_at` on a yes to one call, `reason` when given | The owner answered a request you made. On a yes to a call, make the same call again with the same values: it goes through once before `expires_at`, or always when kept. A yes to an access request shares the component with you. On a no, tell your person and do not try another way around it. | `call_toolkit_tool` |
| `COST_DRIFT` | `direction`, `ratio`, the medians | Read the agent's recent runs and what they cost, then tighten its credit limit or model. | `list_runs`, `get_run_costs`, `update_agent` |
| `INSIGHT_RAISED` | `insight_id`, `insight_type`, `title`, `body`, `suggestion` | Apply the suggestion or dismiss it. An `UPDATE` is news that asks nothing: read it, act on what it reports when that is yours, and acknowledge it with `review_insight` `ACTIONED`. | `claim_insight`, `review_insight` (with the reviewed `prompt` for a prompt fix), `update_agent` |
| `RUN_COMPLETED`, with `agent_ids` set | | Chain the next step on the result. | `get_run`, `create_run` |
| `ENTITY_UPDATED` on an agent | `prompt` with `old` and `new` when the prompt changed | Review the edit, revert or approve it. | `list_edits`, `revert_change` |
| `ENTITY_CREATED` | | Check a new agent's configuration. | `get_agent`, `update_agent` |
| `SECRET_SHADOWED` | `ignored`, `kept`, `names` | Tell the owner which vault items reach the agent under which shared name, so they rename or unassign one. | `send_message` |

Everything else in the activity vocabulary is timeline only and admits no action.
