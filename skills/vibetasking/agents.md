# Agents

An **agent** is the core unit: a configured bundle that an LLM agent executes. You build it with `create_agent` and edit it with `update_agent`, a merge that changes only the fields you send, whose fields are the agent's configuration:

- ``prompt``: the task instructions the agent follows. Author it per **Writing agent prompts** in `building.md`.
- ``name``, ``face``, ``emoji``, ``description``, ``tags``: metadata. ``name`` is the plain title. ``face`` is the icon drawn beside it, a character assembled from the pieces the tool lists (every piece optional, a hat or a tool for the role, a tone to tell siblings apart). ``emoji`` is the alternative when the user wants one, sent instead of ``face`` since setting a face retires the emoji, and a name that starts with the emoji is rejected. ``description`` is user-facing copy shown on the agent's cards and lists: one or two plain sentences, in the user's language, saying what it does and when it runs ("Chases overdue invoices every Monday and reports what changed"), never implementation notes. Runtime settings (model, limits, and so on) are its ``config``, and cascade from the attached preset (see **Run configuration** in `configuration.md`).
- ``public``: visibility. An agent defaults to **private** (``public`` false), seen only inside its workspace. Set ``public`` true to share or publish it. Leave it unset on create and the agent stays private, so set it explicitly when the user asks for a shared one.
- ``folder_id``: the folder the agent lives in. Leave it unset and the agent stays loose at the workspace root, in no folder. Make one with `create_folder` (``name``, ``public``, optionally ``emoji`` and ``description``) and pass its id here. Move an agent later by sending a new ``folder_id``, or null to bring it back to the root. A folder has its own visibility (``public``), and an agent appears inside its folder only when the two ``public`` flags match, and a mismatch is rejected. So a private draft cannot sit in a shared folder: leave it at the root (or in a private folder) until it's published into place. Deleting a folder deletes the agents in it.
- ``preset_id``: the preset whose defaults (model, reasoning, language, fallback, integration defaults) this agent inherits.
- **Its integrations, assets and vault items** are links of their own: `add_agent_integration`, `add_agent_asset` and `add_agent_vault_item` link one, the matching `remove_agent_*` unlinks it, and `list_agent_integrations` and its siblings read them. Read the ids from a **fresh** `list_integrations` right before linking, never from earlier in your conversation: a reconnection may have replaced a row, and a stale id points the agent at the dead connection (known-broken rows are rejected with a 400 only when flagged). When a delegated run reports auth errors on an integration that works for you, compare the integration linked to its agent against the one you use before concluding anything else.
- **Its standing approvals** decide calls of a tool's shape without a fresh answer: `list_agent_approvals` reads them, `create_agent_approval` sets one that asks a person about every such call (``ASK``) or refuses it (``FORBIDDEN``), and `delete_agent_approval` lifts one. See **Lines a tool call can cross** in `building.md`.
- ``form``: a user-input form a person fills in before a run. The value is ``{"fields": [...]}``, each field an object with ``type`` (``text``, ``textarea``, ``number``, ``select`` or ``file``), ``label`` and ``required``, plus per-type options such as ``placeholder``, ``defaultValue`` (camelCase), ``options`` (select), ``min``/``max``/``step`` (number), ``rows`` (textarea) and ``accept``/``multiple`` (file). Any other shape or key is rejected. ``{"fields": []}`` clears it. **Mutually exclusive with triggers and channels.**
- **Triggers** are their own resource: `create_trigger` with the agent's ``agent_id`` adds what fires it, a cron schedule, a Composio/Pipedream integration event, an asset event, or an inbound webhook, which a webhook subscription can point at platform events such as another agent's completed run, and `list_triggers` reads an agent's. See **Triggers** in `building.md`. **Mutually exclusive with forms.**
- **Copying** an agent into another workspace, or a duplicate in its own: `copy_agent` with the ``workspace_ids``, ``dry_run`` first to read what each would get. Its instructions, files, form, configuration, quality checks and schedules (switched off) travel, and each result's ``needs`` lists what stays behind: connections the workspace lacks, secrets, resources, channels, Knowledge, event starts and the learned routine.
- ``recipe``: a previously-distilled successful path (see **Distill a recipe** in `building.md`). Empty until first brew.
- Artifacts: arbitrary files the agent carries across runs (scripts, datasets, configs). See **Resource files (artifacts)** below.

Channels are not an agent field. Attach one by setting its ``agent_id`` with `update_channel` (see **Conventions** in `operations.md`).

"Agent" always means this platform unit here. WhatsApp **message templates** are an unrelated Meta concept that users also call "templates" (see **Routing agents** in `building.md`).

## Resource files (artifacts)

An agent (or preset) can carry **artifact files**: scripts, datasets, or configs the agent reuses across runs. They live on its disk, which every one of its runs mounts, an agent's at ``agent/`` and a preset's at ``preset/``, so the prompt can just invoke one (``python3 agent/sync.py``). This is the right home for a deterministic helper: keep the prompt a thin "run ``agent/<name>``, report its output" wrapper instead of embedding hundreds of lines the agent may re-author (or "improve") on every run.

Files are written to a disk by its id. `create_disk` with ``type`` ``AGENT`` and the ``agent_id`` (or ``PRESET`` and the ``preset_id``) answers that disk, made then when it has none yet, and `get_agent` lists it among its ``mounts``. Write each file with `create_file`, the ``disk_id`` and its ``path`` inside the disk: ``sync.py`` on an agent's disk is ``agent/sync.py`` in its runs. Getting the bytes there differs per surface. Over the MCP, pick the route your file and environment call for:

- **An upload, the default for anything past a few KB.** `create_file_upload` with the ``disk_id`` answers a URL: PUT the raw bytes straight to it (`curl -X PUT --data-binary @./sync.py "<url>"`), then call `create_file` with its ``upload``. Keyless and streamed, so it works from any environment, including an OAuth-connected client whose credential rides the MCP transport and is not yours to send, and the bytes go direct to storage, never through a third-party host. The URL takes one upload and expires, so request it right before uploading.
- **JSON base64, for small files.** `create_file` with ``content_base64``. Needs nothing beyond the MCP connection, but transcribing a large file through base64 is slow and unreliable, so reach for the upload once a file is more than a few KB.
- **``source_url``, when the file already lives at a public https URL.** `create_file` with ``source_url`` has the platform fetch the bytes itself. This is for pulling in a file that is already hosted, not for routing your own bytes through a third party: the upload is the path for bytes you hold.

From a run, `create_file` takes the sandbox ``file_path`` of the file and sends its bytes itself. A file that lives at a public https URL is fetched into the sandbox first (``curl -o``), then written the same way. The reverse, `get_file` with the file's ``file_id`` and an ``output_path``, lands a stored file in your sandbox, and over the MCP `get_file` answers a link to its bytes.

`list_files` with the ``disk_id`` lists what is stored (``path_prefix`` narrows it to one folder), `update_file` moves a file or replaces its bytes, and `delete_file` removes it. Pass the ``expected_sha256`` you read to have a write refused when someone changed the file since.

When the user marks an artifact off-limits (a shared engine script, a config only they maintain), make it real with `create_disk_rule`: ``type`` ``LOCKED`` and the file's ``path``, or a folder's ending in ``/``. No run writes past a lock, its own disk's included, while a person editing in their own name still may. `list_disk_rules` shows the locks and `delete_disk_rule` lifts one when they release it. A rule of ``type`` ``WRITABLE`` naming an ``agent_id`` lets that agent's conversations, its runs with no person behind them, write the path, which they otherwise only read.
