# Agents

An **agent** is the core unit: a configured bundle that an LLM agent executes. You build and edit it through `upsert_agent`, whose fields are the agent's configuration:

- ``prompt``: the task instructions the agent follows. Author it per **Writing agent prompts** in `building.md`.
- ``name``, ``face``, ``emoji``, ``description``, ``tags``: metadata. ``name`` is the plain title. ``face`` is the icon drawn beside it, a character assembled from the pieces the tool lists (every piece optional, a hat or a tool for the role, a tone to tell siblings apart). ``emoji`` is the alternative when the user wants one, sent instead of ``face`` since setting a face retires the emoji, and a name that starts with the emoji is rejected. ``description`` is user-facing copy shown on the agent's cards and lists: one or two plain sentences, in the user's language, saying what it does and when it runs ("Chases overdue invoices every Monday and reports what changed"), never implementation notes. Runtime settings (model, limits, and so on) are *not* set here. They live on ``data`` and cascade from the attached preset (see **Run configuration** in `configuration.md`).
- ``public``: visibility. An agent defaults to **private** (``public`` false), seen only inside its workspace. Set ``public`` true to share or publish it. Leave it unset on create and the agent stays private, so set it explicitly when the user asks for a shared one.
- ``folder_id``: the folder the agent lives in. Leave it unset and the agent stays loose at the workspace root, in no folder. There is no folder endpoint: create one with `insert_data` on ``folders`` (``workspace_id``, ``profile_id``, ``name``, ``public``, optionally ``emoji`` and ``description``), read back the new row's id, and pass it as ``folder_id`` here. Move an agent later by sending a new ``folder_id``. A folder has its own visibility (``folders.public``), and an agent appears inside its folder only when the two ``public`` flags match, and `upsert_agent` rejects a mismatch. So a private draft cannot sit in a shared folder: leave it at the root (or in a private folder) until it's published into place.
- ``preset_id``: the preset whose defaults (model, reasoning, language, fallback, integration defaults) this agent inherits.
- ``integration_ids`` and ``asset_ids``: the integrations and assets the agent may use. Read the ids from a **fresh** ``integrations`` listing right before linking, never from earlier in your conversation: a reconnection may have replaced a row, and a stale id points the agent at the dead connection (known-broken rows are rejected with a 400 only when flagged). When a delegated run reports auth errors on an integration that works for you, compare the integration id on its agent against the one you use before concluding anything else.
- ``form``: a user-input form a person fills in before a run. The value is ``{"fields": [...]}``, each field an object with ``type`` (``text``, ``textarea``, ``number``, ``select`` or ``file``), ``label`` and ``required``, plus per-type options such as ``placeholder``, ``defaultValue`` (camelCase), ``options`` (select), ``min``/``max``/``step`` (number), ``rows`` (textarea) and ``accept``/``multiple`` (file). Any other shape or key is rejected. ``{"fields": []}`` clears it. **Mutually exclusive with triggers.**
- ``triggers``: what fires the agent: a cron schedule, a Composio/Pipedream integration event, an asset event, or another agent completing a run. See **Triggers** in `building.md`. **Mutually exclusive with forms.**
- ``recipe``: a previously-distilled successful path (see brewing). Empty until first brew.
- Artifacts: arbitrary files the agent carries across runs (scripts, datasets, configs). See **Resource files (artifacts)** below.

Channels are not an `upsert_agent` field. Attach one by setting its ``agent_id`` via `upsert_channel` (see **Conventions** in `operations.md`).

"Agent" always means this platform unit here. WhatsApp **message templates** are an unrelated Meta concept that users also call "templates" (see **Routing agents** in `building.md`).

## Resource files (artifacts)

An agent (or preset) can carry **artifact files**: scripts, datasets, or configs the agent reuses across runs. At run start each one becomes available to the agent inside its sandbox at ``agent/<name>``, so the prompt can just invoke it (``python3 agent/sync.py``). This is the right home for a deterministic helper: keep the prompt a thin "run ``agent/<name>``, report its output" wrapper instead of embedding hundreds of lines the agent may re-author (or "improve") on every run.

Getting bytes into an entity differs per surface. Over the MCP, pick the route your file and environment call for:

- **Presigned upload, the default for anything past a few KB.** Call `get_upload_url(entity_type="agent", entity_id=..., path="sync.py")`, then PUT the raw bytes straight to the URL it returns: `curl -X PUT --data-binary @./sync.py "<url>"`. Keyless and streamed, so it works from any environment, including an OAuth-connected client whose credential rides the MCP transport and is not yours to send, and the bytes go direct to storage, never through a third-party host. The URL is single-use and short-lived, so request it right before uploading. `path` is fixed when the URL is signed, so the bytes can only land where your grant allows.
- **JSON base64, for small files.** `upload_file_to_entity(entity_type="agent", entity_id=..., path="sync.py", content_base64=...)`. Needs nothing beyond the MCP connection, but transcribing a large file through base64 is slow and unreliable, so reach for the presigned upload once a file is more than a few KB.
- **``source_url``, when the file already lives at a public https URL.** `upload_file_to_entity(entity_type="agent", entity_id=..., source_url="<that url>")` has the server fetch the bytes itself (`path` defaults to the URL's filename). This is for pulling in a file that is already hosted, not for routing your own bytes through a third party: the presigned upload is the path for bytes you hold.

From a run, `upload_file_to_entity(entity_type="agent", entity_id=..., file_path="sync.py")` sends the file at that sandbox path and stores it under the same name. A file that lives at a public https URL is fetched into the sandbox first (``curl -o``), then uploaded the same way. The reverse, `download_file_from_entity` with the entity and the file's ``path``, lands a stored file in your sandbox (``output_path`` picks where).

Confirm the stored bytes with `list_files_in_entity`, and remove one with `delete_file_from_entity`.

When the user marks an artifact off-limits (a shared engine script, a config only they maintain), make it real with `protect_file_in_entity` (or ``protected: true`` on the upload): the file materialises read-only in every sandbox and agent writes to it are refused, backing the instruction with an actual guard. `list_files_in_entity` shows the protected set, and the same call clears the flag when they release it.
