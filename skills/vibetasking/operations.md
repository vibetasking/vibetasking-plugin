# Secrets and credentials

Use secrets by reference, not by value. Credentials live in the workspace **Vault** as typed items (LOGIN, PASSWORD, CREDIT_CARD, IDENTITY, VARIABLE, TOKEN) that users assign to agents. The app shows people the Vault as **Secrets**, so a message to a person calls it Secrets, in their language, never the Vault. A run resolves the fields of every item assigned to its agent, and the prompt (or the agent) references a field as ``$NAME`` in any shell command or tool argument: the slug uppercased with dashes as underscores, suffixed with the field for a multi-field item (``$ACME_PORTAL_USERNAME``, ``$CARD_HOLDER``), bare for a PASSWORD or TOKEN item (``$STRIPE``), and the item's own ``variable`` for a VARIABLE. Every item response and `list_vault_items` carry each field's ``exposed_name``, the exact spelling to use. A LOGIN, PASSWORD or CREDIT_CARD field is closed: the sandbox holds a stand-in the platform swaps for the real value only on its way out, to a site or an API, so the value never enters a prompt, a trace, or your context. An IDENTITY or VARIABLE field is readable: the sandbox holds the value itself. A TOTP field yields a fresh 6-digit code on every use. A TOKEN item holds a signing key or a client secret, and its name stands for the short lived token the platform signs or fetches from it on each HTTPS request to the item's hosts, so the agent puts ``$NAME`` where the service expects its token and neither the key nor the token enters the sandbox.

A PASSWORD item whose value is a POSTGRES, MYSQL, MONGODB, REDIS, SMTP, IMAP, AMQP, MQTT or LDAP connection URL is a server the platform signs into on the agent's behalf for the length of each run, and the agent's environment carries the variable as a local URL with a run-scoped token, plus ``NAME_HOST``, ``NAME_PORT``, ``NAME_USER``, ``NAME_PASSWORD`` and, where the protocol has a database, ``NAME_DATABASE``, so ``psql``, ``mysql``, ``mongosh``, ``redis-cli``, ``curl``, ``amqp-get``, ``mosquitto_sub`` and ``ldapsearch`` connect as the vendor documents while the real password never reaches the agent. Every part of the URL beside its password is derived from it and answered as the item's ``data`` (``engine``, ``scheme``, ``host``, ``port``, ``user``, ``database``, ``options``), so a stored server can be read and changed without the credential. The same shapes exist as flat secrets through `create_secret` with ``type`` POSTGRES, MYSQL, MONGODB, REDIS, SMTP, IMAP, AMQP, MQTT, LDAP or ENV, where ``name`` is the variable, whose ``connection`` answers the same parts, and `test_secret` signs into a connection secret once from the platform and reports how it went. Such a server is never an integration: nothing connects it, the secret is the connection.

Never paste a raw credential into a prompt, a message, or a tool argument, except the fields whose job is to receive the plaintext once: a vault item's ``fields`` and ``connection`` (`create_vault_item`, `update_vault_item`), a secret's ``value`` (`create_secret`, `update_secret`), and an integration's ``credentials`` and ``headers`` (`create_integration`, `update_integration`). Each is encrypted at rest and never answered (reads give a masked ``••••`` preview or none).

Managing the Vault:

- **`create_vault_item`** creates a typed item, owned by you: ``workspace_id``, ``type``, ``title``, an optional ``slug`` (the agent-facing name prefix, immutable, defaulting to a slugified title), and ``public`` (false = personal to the owner, true = shared with the workspace). Plain display fields go in ``data`` (e.g. LOGIN: ``username``, ``allowed_hosts``) and concealed values in ``fields`` (e.g. LOGIN: ``password``, ``totp``; PASSWORD: ``password``, a value or a connection URL; CREDIT_CARD: ``number``, ``cvv``; TOKEN: ``secret``, the key or client secret, with ``source`` and the keys that source needs in ``data``). ``allowed_hosts`` (on LOGIN, PASSWORD, CREDIT_CARD and TOKEN) lists the exact hostnames the item's concealed fields reach without asking, and any other host asks for approval on the run first. An item without hosts can carry the member's confirmation instead, ``any_host: true``, which sends its concealed fields to any host without asking, in every run. **`update_vault_item`** changes one as a merge: ``data`` keys set or deleted, and ``fields`` three-state per key: a string sets or rotates, ``null`` keeps what is stored, ``""`` deletes. A connection URL can go in ``connection`` as its parts (``scheme``, ``host``, ``port``, ``user``, ``password``, ``database``, ``options``) instead of in ``fields.password`` as one string: the platform assembles and validates it, so nothing is percent-encoded by hand, and omitting ``password`` on an item that already holds a connection keeps the stored one. ``agent_ids``, when sent, sets the item's agent assignments to exactly that list.
- **`list_vault_items`** (optional ``agent_id`` filter) and **`get_vault_item`** answer metadata, per-field ``configured`` state with the agent-facing ``exposed_name``s, and the item's current ``agent_ids``. Stored values are never answered. **`delete_vault_item`** removes the item, its stored values, and its assignments. To assign an existing item to one more agent, `add_agent_vault_item` on that agent, and `remove_agent_vault_item` takes it off.
- **The quick path for one value:** `create_secret(table_name="agents", record_id=<agent id>, name, value)` lands in the Vault too: when ``name`` already resolves through an item assigned to that agent, the matching field is rotated in place. Otherwise a fresh single-field item is created, assigned to the agent, and resolves under ``$NAME`` (its slug uppercased). Pass ``type="TOTP"`` when the value is a 2FA seed. The ``workspaces`` / ``presets`` / ``runs`` tables store flat secrets through the same call, for the rare credential that isn't agent work.
- `list_secrets(table_name, record_id)`, `get_secret`, `update_secret` and `delete_secret` cover those flat secrets with redacted previews. For an agent, `list_secrets` also flattens the assigned vault items' fields into the same shape, each under its agent-facing name plus a ``vault_item_id``.

When the same name resolves at several scopes, the most specific wins: run > agent-assigned vault items > preset > workspace.

Integration credentials are separate. Don't store them as generic secrets:

- Use `create_integration` and `update_integration`: env-style credentials in ``credentials``, MCP HTTP headers (e.g. ``Authorization``) in ``headers``. On an update each is three-state per key: string = set/rotate, ``null`` = preserve existing, omitted key = delete.

# Triage

`list_activities` with ``inbox=true`` lists the severity-bearing activities (low credit, integration reauth needed, run failures with a fix variant, evaluation failures, webhook deliveries failing, missed triggers, …). Each carries an ``action`` naming the ``operation`` that settles it, plus the minimum ``hint`` arguments for that call. `acknowledge_activity` dismisses one without resolving the underlying condition (partner-driven dismissal, not state reversal), and `wait_for_activities` holds until new ones arrive.

Some inbox activities are **suggestions** (``INSIGHT_RAISED``): findings from the platform's nightly review of the workspace's runs, each backed by an insight whose id rides in the activity's ``data.insight_id`` (`get_insight` reads it). When the user hands one to you (the briefing names the insight id), judge it against the agent's configuration and recent runs, and close it with `review_insight` once settled: ``ACTIONED`` when the fix was applied with the user's confirmation, ``DISMISSED`` with a ``reason`` when it does not apply. A prompt fix the user confirmed lands with the review in one call: `review_insight` with ``ACTIONED`` and the agent's whole reviewed ``prompt``, so the agent never runs the new prompt while its suggestion still reads as open. The reason feeds the next nightly review, so record the verified facts, not a pleasantry. `claim_insight` marks which run took a finding and clears its card while the insight stays PENDING (the app calls it when handing off, you rarely need it). Prefer `review_insight` over `acknowledge_activity` on a suggestion: a bare acknowledge records the finding as won't-fix.

The inbox is only the severity-bearing subset of the activities, the platform's full event log: every message insert (``MESSAGE_INSERTED``), every run state change (``RUN_QUEUED``, ``RUN_EXECUTED``, ``RUN_WAITING``, ``RUN_COMPLETED``, ``RUN_FAILED``, …), webhook deliveries, and insights. When you need to reconstruct what happened and when (a run that seems stuck, a message that never dispatched, a trigger that did or didn't fire), `list_activities` filtered by ``record_id`` (the run or message id) with ``sort=created_at`` is the debugging timeline, cheaper and often more direct than reading the full trace.

**Notifications.** Besides the inbox, news reaches a person by push and by email as their notification settings say. `list_notification_settings` lists how each kind of news reaches the person your key acts for in a workspace, one setting per ``scope`` (``RUN`` a finished run, ``HELP`` a run that failed, is blocked or waits for someone, ``OPERATOR`` a conversation waiting for a person or a message in one they hold, ``COST`` an agent spending past its usual range, ``DIGEST`` the weekly summary, and the rest its description names). `update_notification_setting` turns ``push`` or ``email`` on or off for one ``scope``, and a ``locked`` setting (``CREDITS``, ``CONNECTIONS``, ``TRIGGERS``) always stays on. The person finds the same switches in the app's settings, under Notifications.

# Webhooks

`list_activities` is the pull side. Webhooks are the push side. `create_webhook(workspace_id, url, …)` subscribes an external URL to your workspace's activities. The response answers a signing ``secret`` **once**, never readable later, so store it on the receiving end to verify each delivery's HMAC signature. Pass ``version`` 3 for Standard Webhooks delivery: a ``whsec_`` secret any Standard Webhooks library verifies, a verification request the endpoint answers with its ``challenge`` before the first delivery, and retries under the same ``webhook-id``. Narrow what fires with the ``preset_ids``, ``agent_ids``, and ``activity_types`` filter arrays (``activity_types`` takes the same activity type names the activities carry). `update_webhook` replaces each array it is sent. List your subscriptions (secret redacted) with `list_webhooks`, remove one with `delete_webhook`.

**Reacting to events with an agent.** Give the agent an activity trigger (`create_trigger` with ``activity``): at most hourly it starts a run of that agent over the matching events since its last fire, so an agent can admit a contact waiting at a gated channel, re-dispatch a failed run or chase a low balance through the API. Name the watched agents in ``agent_ids``, only the kinds the agent handles in ``activity_types``, and write what to do for each kind into its prompt. Webhook subscriptions are for systems outside the platform. Read the ``platform-events`` skill (`get_skill` over the MCP, ``system/skills/platform-events/SKILL.md`` from a run) before wiring one: it carries the fire's shape and, per kind, what a reacting agent can do and which operation settles it.

# API keys

`create_key` mints a durable key for you, for code that outlives this conversation: a deployed app, an external script, a webhook receiver. Pass a ``name`` saying what it's for and explicit ``scopes`` (``resource:verb`` strings like ``runs:read``, ``runs:create``, or an ``action:`` name like ``action:call_tools``, and a scoped caller can only grant scopes it holds). Each operation in the API document lists what it needs as ``x-scopes``, and a name outside the vocabulary is refused. Omit ``workspace_id`` for a key that acts across every workspace you belong to, and ``expires_at`` for a non-expiring key. A key you mint keeps this conversation: it carries your safeguards, and canceling or deleting the conversation revokes it, so tell the user. The response carries ``token`` exactly once (only its hash is stored), so put it where it's needed immediately and never echo it back. `list_keys` and `delete_key` cover rotation and cleanup.

# Billing

Everything runs on workspace credits: one credit is one cent ($0.01) of value.

**Plan and balance.** `get_billing` is the authoritative answer to "what plan is this workspace on" and "how many credits are left": the effective plan, account type, payment method, spendable balance (``credit_total``), run concurrency, ``linked`` (the billing account was originated by another workspace), ``shared`` (more than one workspace runs on it, so the plan, balance, and purchases are pooled across all of them), and its auto-recharge under ``recharge``.

**The catalog.** `list_plans` lists the subscription plans and the credit packages: each with its price, the credits it includes and, for a plan, the run concurrency it grants. Read it before you name a plan or a price, and pass the ``name`` it returns to `create_checkout_session`.

When the balance or the plan is the blocker (a ``LOW_CREDIT`` activity, or the ``CREDITS_EXHAUSTED`` one that lists every run stopped on the balance) you can't fix it yourself. From a run a member owns, ask with ``message_user``, ``action`` ``provide`` and ``data`` ``{"kind": "credits"}``: the card offers a plan when there is none and credits when there is one, so a run never sends a checkout link. Over the MCP, generate a URL for the user to open, and let `get_billing` decide which. **Credits are sold only on an active subscription.** While ``plan`` is null the workspace has none, so the link is `create_checkout_session(mode="subscription", plan=...)` whatever the user asked to buy: offer the plans `list_plans` answers, mint the checkout for the one the user picks, and the plan's monthly credits are the top-up. A credit package checkout answers 402 there. With a plan, `create_checkout_session(mode="payment", package=...)` buys credit packages on top of it (``quantity`` at least the package's ``minimum_quantity`` from `list_plans`), `create_checkout_session(mode="subscription", plan=...)` changes the plan (an already-active subscription gets a portal flow URL instead), and `create_billing_portal_session` manages the existing subscription and payment methods. Nothing is charged by the calls themselves. Both need an ADMIN profile and the ``action:manage_billing`` scope.

**Cost reporting.** `list_usage` answers "what did this workspace spend, on what": a time-bucketed series of credits consumed, grouped by cost category (``agent``, ``voice``, ``sms``, ``email``, ``asset_usage``, ``asset_rental``, ``asset_purchase``, ``evaluation``, ``adjustment``, ``other``). Pass ``start``/``end`` (ISO-8601) and ``bucket_width`` ``1d`` (default), ``1h`` or ``1mo``, and add ``group_by=agent_id`` to split by automation, ``asset_id`` to split by asset. Debits only, credit purchases are not in it. Buckets answer ``next_cursor``: feed it back as ``cursor``, null when there are no more. Needs an ADMIN profile and the ``usage:read`` scope. `get_run_costs` breaks one run down: which models ran and their request counts (the main agent's alongside its sub-agents' and auxiliary calls'), stipend and soft-limit floor, the per-use asset costs the run caused (SMS segments, call telephony, billed to the balance but not part of ``credit_used``), and evaluation spend. Every figure in both reports is a credit count, a cent of value each.

**Referrals.** Every person has a referral code of their own. `get_referral_code` answers the code and its signup link, what someone who signs up with it receives, what the person earns from what those people pay, and the balance left to redeem, in euro cents. `list_referrals` lists who signed up with it, and `redeem_referral_balance` moves the balance, or part of it, into a workspace's credits, one credit per cent, for a person whose role buys credits there. A payout by bank transfer is arranged with the platform by writing in, from the app's settings, under Referrals.

# Removing what you connected

Disconnecting a channel, releasing an asset and removing an integration are deletes: `delete_channel`, `delete_asset` and `delete_integration`. The platform runs the provider teardown behind each one (a WhatsApp number is deregistered at Meta, a Telegram webhook dropped, a Twilio number or a Supabase project released, a Composio account deleted), so nothing else is needed and nothing else must be done first. Read the links before deleting (`list_agent_assets`, `list_agent_integrations`, the channel's ``agent_id``): every agent wired to it loses that backing at once. An asset release ends its rental and is irreversible (a released database is gone with its data), and a channel delete ends every conversation on it, so confirm with the user and name what disappears. Deleting an agent, a preset or a folder is `delete_agent`, `delete_preset` or `delete_folder`, and a folder takes its agents with it.

# Workspaces and members

A workspace is created with `create_workspace`: a ``name``, optionally ``share_billing_with`` (a workspace you own, so the new one runs on the same subscription and balance rather than a fresh trial of its own) and ``partner_id`` (a partner organisation you are an admin of, when the workspace is a client of the partner program). You are its ``OWNER`` on creation. It needs an account and a key across every workspace, since a key pinned to one workspace cannot act in the new one (see **First contact and billing** in `SKILL.md`).

Invite someone with `create_invitation` (``workspace_id``, ``email``, ``role`` as ``OWNER``, ``ADMIN``, ``MEMBER`` or ``DUMMY``, a viewer): the invitation email goes out with the call, so never call it to "prepare" one. Only an owner invites an ``OWNER`` or an ``ADMIN``. `list_invitations` lists the pending ones, and `delete_invitation` withdraws one. `list_members` lists the members with their ``role``: `update_member` changes a role and `delete_member` removes the member, an ADMIN changes and removes members and viewers, an OWNER admins and owners too, and the last owner can neither leave nor step down. Never change your own role or remove yourself: those are the owners' calls in the app. `get_me` lists the workspaces the profile belongs to, and `update_workspace` renames one when the user asks. It also sets ``supervision`` (``OFF``, ``SUGGEST``, or ``AUTONOMOUS``, which only an owner sets) and, on Enterprise and for an owner alone, who manages credentials and channels (``manage_role``), the email domains whose people may join (``join_domains``), required two-step verification (``mfa_required``), how long activity records are kept (``retention_months``) and whether anonymous usage improves the service (``improvement``). A run never changes any of these, and an update refused on one field changes none.

# Company record

`update_workspace` with ``company`` keeps the workspace's company record (``name``, ``url``, ``logo``, ``description``, ``sector``, ``size``, ``departments`` and ``facts``), written back whenever the user teaches you something about the company, and `get_workspace` reads it. ``branding`` (``name``, ``color``, ``logo``, the path of a file on one of its agents' disks) is how the pages a contact opens to connect an account show the workspace.

# Sharing and housekeeping

- **Sharing inside the workspace.** A grant shares one agent, preset, folder, channel, integration, asset, named disk or vault item with one member at ``VIEWER``, ``EDITOR`` or ``MANAGER`` level: `create_grant` with ``table_name`` (``agents``, ``presets``, ``folders``, ``channels``, ``integrations``, ``assets``, ``disks`` or ``vault_items``), ``record_id``, ``grantee_id`` (the member) and ``level``, `list_grants` and `delete_grant` beside it. Only the owner, a workspace admin or a MANAGER grantee may write them. ``public`` on the record itself shares it with the whole workspace instead.
- **Sharing outside.** `create_agent_share` with an ``expires_at`` answers a public link that starts a run of the agent for whoever opens it, shown that once, `list_agent_shares` lists an agent's links, `update_agent_share` moves one's ``expires_at`` while its link stays the same, and `delete_agent_share` revokes one.
- **Archiving and renaming.** ``archived_at`` on `update_run` or `update_agent` archives a run or an agent, ``null`` restores it. Assets are renamed with `update_asset` (``name``), which takes a SUPABASE, PROXY or LINKEDIN asset, runs with `update_run`'s ``name``, and everything else through its own update.
- **Spending guards.** `get_billing`'s ``recharge`` and `update_billing` read and set the auto-recharge knobs (the balance that triggers a top-up, the balance it refills to, the monthly ceiling). Both need an ADMIN profile, the update needs the ``action:manage_billing`` scope, and they are the user's numbers to set: never pick a ceiling for them. Auto-recharge buys credits, so it runs only on an active subscription: without a plan it never buys, and turning it on answers 402.
- **Phone numbers.** `get_tollfree_verification` / `submit_tollfree_verification` carry a US toll-free number through carrier verification, and `list_number_countries` says per country which number types need a regulatory bundle (see **Assets** in `wiring.md` for bundles).
- **Databases.** `get_database_options` lists the compute sizes a SUPABASE asset can move to with their credit cost, and `resize_database` applies one.

# Partner tools

When the user belongs to a partner org, a small tool set reads and manages the partner's client workspaces. It answers only a connection to every workspace, such as the connector or an account-wide API key: a run's own tools leave it out, and a key pinned to one workspace is refused. Every call needs a ``partner_id``: `get_me` returns a ``partners`` list with each org's id and the user's role there. If it's empty, the user isn't a partner member, so don't call these tools. `list_partner_deployments` works for any partner member, and the rest need an ADMIN or OWNER partner role and return 403 otherwise.

The tools: `list_partner_client_usage` (one client workspace's consumption, same shape and parameters as `list_usage`), `list_partner_deployments` (self-hosted appliance installs: heartbeat, license summary, run telemetry), and the pricing surface (`get_partner_client_premiums`, `update_partner_client_premiums`), which reads and merges the client's ``stipend`` / ``multiplier`` / ``soft_limit`` for the workspace and per agent under ``agents`` (writes need the ``action:manage_partner`` scope, and pricing is only available to partners without a flat commission rate). A client workspace joins the program by carrying the partner's id, passed as ``partner_id`` to `create_workspace` when the partner sets it up. Commission, payout, and cross-client evaluation reporting live in the partner dashboard, not the API.

# Conventions

- Every resource lives under a workspace. A create takes ``workspace_id`` (a key pinned to one workspace may leave it out), and what you create is yours: the platform names your profile as its owner.
- An `update_*` takes the resource's id in its path and changes only the fields present in the body. Omitting a field leaves it as-is, and ``null`` clears one that may be cleared.
- **Objects merge.** ``config`` on an agent, a preset or a trigger merges key by key (a value sets, ``null`` deletes, an omitted key is left alone), so change one key without resending the rest. ``form`` and ``recipe`` are replaced whole when sent, and a ``null`` ``recipe`` deletes it (see **Build and iterate on an agent → Distill a recipe** in `building.md`).
- An array is replaced whole when sent. A relation several writers change is its own sub resource: an agent's or a preset's integrations, assets and vault items are linked and unlinked one at a time (`add_agent_integration`, `remove_agent_integration` and their siblings), and triggers are created, updated and deleted one at a time. ``tool_policies`` on an integration is a map from tool name to ``allowed``, ``forbidden`` or ``approval``, replaced whole: send an empty object to clear it.
- `update_channel` changes ``public``, ``agent_id`` and ``settings``, and requires the right to edit the channel. ``settings`` carries the channel's runtime behavior: ``delay``/``jitter`` (humanizing reply delay in seconds), ``hours`` (scheduled agent hours: IANA ``tz`` + per-day ``windows``, and outside them conversations park until the next window), ``operator_timeout`` (seconds of operator silence before the agent takes back the conversation), ``access_list`` (sender gating with ``mode`` allow/block and ``entries``), ``replies`` (the messages the channel sends a contact on its own, each ``{on, text}``), ``reach_external`` (off by default: the conversation's run may only message, cc, or call its own bound contact, and sends naming anyone else are refused, so cc'ing a supervisor or notifying a third party needs it on), ``silent_handoff`` (off by default: when on, ``dispatch_human`` mutes the agent instead of switching the conversation to operator mode. The workspace is notified, the contact gets nothing, and the conversation keeps dispatching on the contact's messages with every channel send refused, so the agent keeps recording while a person talks natively on the account), and ``handoff_notify`` (workspace member profile ids notified per contact message while a handoff holds the conversation, on top of anyone subscribed to the agent or workspace: with nobody at all to notify, the agent's owner is, so a held conversation never goes unwatched). See the tool schema for shapes. Each key you send replaces that setting, and an explicit ``null`` clears one. ``settings`` also applies on create, so pass it in the same call that connects the channel. **Working hours, reply pacing and sender gating live here, never in a prompt**: an agent instructed to "only answer between 9 and 18" still dispatches a run for every inbound message and spends a turn on it, while ``hours`` parks the conversation until the window opens. A channel's contacts, read with `list_contacts`, move between its allow and block lists with `update_contact`. A channel ``disconnected`` stays reachable by nobody until it is connected again from the app: repointing its agent changes nothing.
- Error responses share one envelope, ``{"error": {"code", "message", "status", "param", ...}}`` (see `data.md`). When a Composio call fails, ``message`` carries the upstream message and any suggested fix.
- Vocabulary: ``sandbox`` (not "workspace") for the filesystem the agent works in, ``action`` (not "tool") at the composio/pipedream second level, ``recipe`` (not "flow") for a distilled run.
- The tool schemas over the MCP, and each action's ``--help`` from a run, are the authoritative contract: each operation's description and parameter shapes travel with the operation itself. This guidance is the map, not the spec. When the two disagree, trust the schema or the help text.

# Worked examples: from a request to platform actions

How a user's ask (in their vocabulary) decomposes into platform actions. Illustrative, not exhaustive: the decision rules live in the files above.

**"Every Monday, email me a sales summary."** Recurring and unattended → an agent with a trigger. (1) `list_providers` for the data source, and if it isn't connected, request the connection rather than guessing credentials. (2) `create_agent`: prompt per **Writing agent prompts** in `building.md`, a user-facing ``description``, and no ``preset_id`` unless the user named a tier (see **Choosing a tier** in `configuration.md`), then `add_agent_integration` for the source. (3) `create_trigger` with ``cron`` ``"0 9 * * 1"`` and the user's ``timezone``. (4) Announce, then test with `create_run` and read `get_run_trace`. Not: running it by hand every Monday, adding a ``form`` (nothing to fill), or guessing a ``trigger_slug`` without `list_providers`.

**"Download this portal's invoices for me, now."** One-off → a bare `create_run` with the whole brief in ``text`` (browsing included), then deliver the files the settled run attached. Offer to save it as an agent only if it looks recurring. Not: building an agent first, which leaves persistent clutter for a single execution.

**"Re-engage my old clients over WhatsApp and get them to book appointments. Their data is scattered across spreadsheets and old exports."** A multi-piece build like this is what **packages** are for. The `whatsapp-reengagement` package carries the full blueprint: a shared database asset at the center, one preset carrying the shared persona, one thin conversational agent per number, cron-fired launcher agents doing the outreach, and a sync agent closing the loop. `get_package` it and follow its build order rather than improvising the decomposition. Not: one giant agent doing outreach, conversation, and sync, the client list pasted into prompts instead of the database, or all the volume through one number.

**"Set my client up: they need an agent answering their WhatsApp."** A builder working for a client → a workspace of the client's own. (1) `create_workspace` with the client's name, sharing your billing when the user says you carry the subscription. (2) Build the agent in it and connect the channel there. (3) `create_invitation` with the client's email as ``OWNER`` once it runs, so the client changes its plan and its people on its own. (4) When the client pays for themselves, hand them a `create_checkout_session` link for their workspace. Not: building in the user's own workspace and moving it later, or inviting the client before the first demonstrated run.
