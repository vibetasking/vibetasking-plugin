# Secrets and credentials

Use secrets by reference, not by value. Credentials live in the workspace **Vault** as typed items (LOGIN, PASSWORD, CREDIT_CARD, IDENTITY, VARIABLE) that users assign to agents. A run resolves the fields of every item assigned to its agent, and the prompt (or the agent) references a field as ``$NAME`` in any shell command or tool argument: the slug uppercased with dashes as underscores, suffixed with the field for a multi-field item (``$ACME_PORTAL_USERNAME``, ``$CARD_HOLDER``), bare for a PASSWORD item (``$STRIPE``), and the item's own ``variable`` for a VARIABLE. Every item response and `list_vault_items` carry each field's ``exposed_name``, the exact spelling to use. A LOGIN, PASSWORD or CREDIT_CARD field is closed: the sandbox holds a stand-in the platform swaps for the real value only on its way out, to a site or an API, so the value never enters a prompt, a trace, or your context. An IDENTITY or VARIABLE field is readable: the sandbox holds the value itself. A TOTP field yields a fresh 6-digit code on every use.

A PASSWORD item whose value is a POSTGRES, MYSQL, MONGODB, REDIS, SMTP, IMAP, AMQP, MQTT or LDAP connection URL is a server the platform signs into on the agent's behalf for the length of each run, and the agent's environment carries the variable as a local URL with a run-scoped token, plus ``NAME_HOST``, ``NAME_PORT``, ``NAME_USER``, ``NAME_PASSWORD`` and, where the protocol has a database, ``NAME_DATABASE``, so ``psql``, ``mysql``, ``mongosh``, ``redis-cli``, ``curl``, ``amqp-get``, ``mosquitto_sub`` and ``ldapsearch`` connect as the vendor documents while the real password never reaches the agent. Every part of the URL beside its password is derived from it and returned in ``data`` (``engine``, ``scheme``, ``host``, ``port``, ``user``, ``database``, ``options``), so a stored server can be read and changed without the credential. The same shapes exist as flat rows through `upsert_secret` with ``type`` POSTGRES, MYSQL, MONGODB, REDIS, SMTP, IMAP, AMQP, MQTT, LDAP or ENV, where ``name`` is the variable, and `test_secret_connection` signs into a connection secret once from the platform and reports how it went. Such a server is never an integration: nothing connects it, the secret is the connection.

Never paste a raw credential into a prompt, a message, or a tool argument. The **one** exception is `upsert_secret`'s ``value`` field, whose job is to receive the plaintext once. It is encrypted at rest and never returned (reads give a masked ``••••`` preview).

Managing the Vault:

- **`upsert_vault_item`** creates or updates a typed item. On create: ``workspace_id``, ``type``, ``title``, an optional ``slug`` (the agent-facing name prefix, immutable, defaulting to a slugified title), and ``public`` (false = personal to the owner, true = shared with the workspace). Plain display fields go in ``data`` (e.g. LOGIN: ``username``, ``website``) and concealed values in ``fields`` (e.g. LOGIN: ``password``, ``totp``; PASSWORD: ``password``, a value or a connection URL; CREDIT_CARD: ``number``, ``cvv``). ``fields`` is three-state per key: a string sets or rotates, ``null`` keeps what is stored, ``""`` deletes. A connection URL can go in ``connection`` as its parts (``scheme``, ``host``, ``port``, ``user``, ``password``, ``database``, ``options``) instead of in ``fields.password`` as one string: the platform assembles and validates it, so nothing is percent-encoded by hand, and omitting ``password`` on an item that already holds a connection keeps the stored one. ``agent_ids``, when provided, reconciles the item's agent assignments to exactly that list.
- **`list_vault_items`** (optional ``agent_id`` filter) and **`get_vault_item`** return metadata, per-field ``configured`` state with the agent-facing ``exposed_name``s, and the item's current ``agent_ids``. Stored values are never returned. **`delete_vault_item`** removes the item, its stored values, and its assignments. To assign an existing item to another agent, read its ``agent_ids``, append, and send the full list back through `upsert_vault_item`.
- **The quick path for one value:** `upsert_secret(workspace_id, table_name="agents", record_id=<agent id>, name, value)` lands in the Vault too: when ``name`` already resolves through an item assigned to that agent, the matching field is rotated in place. Otherwise a fresh single-field item is created, assigned to the agent, and resolves under ``$NAME`` (its slug uppercased) and exactly ``<secret>name</secret>``. Pass ``type="TOTP"`` when the value is a 2FA seed. The ``workspaces`` / ``presets`` / ``runs`` scopes still store flat rows through the same tool, for the rare credential that isn't agent work.
- `list_secrets(table_name, record_id)` and `delete_secret(secret_id)` cover those flat scopes with redacted previews. For an agent, `list_secrets` also flattens the assigned vault items' fields into the same shape, each under its agent-facing name plus a ``vault_item_id``.
- The ``secrets`` table itself is **not** reachable through the Data tools (`query_data` / `update_data` / `delete_data` are refused on it). Always go through the tools above.

When the same name resolves at several scopes, the most specific wins: run > agent-assigned vault items > preset > workspace.

Integration credentials are separate. Don't store them as generic secrets:

- Use `upsert_integration`: env-style credentials in ``credentials``, MCP HTTP headers (e.g. ``Authorization``) in ``headers``. Update semantics are three-state per key: string = set/rotate, ``null`` = preserve existing, omitted key = delete.

# Triage

`list_inbox` returns severity-bearing activity rows (low credit, integration reauth needed, run failures with a fix variant, evaluation failures, webhook deliveries failing, missed triggers, …). Each row carries an ``action.verb`` naming the operation that resolves it, plus the minimum ``hint`` arguments for that call. Use `acknowledge_inbox_item` to dismiss a row without resolving the underlying condition (partner-driven dismissal, not state reversal).

Some inbox rows are **suggestions** (``INSIGHT_RAISED``): findings from the platform's nightly review of the workspace's runs, each backed by an ``insights`` row whose id rides in the activity's ``data.insight_id``. When the user hands one to you (the briefing names the insight id), judge it against the agent's configuration and recent runs, and close it with `review_insight` once settled: ``ACTIONED`` when the fix was applied with the user's confirmation, ``DISMISSED`` with a ``reason`` when it does not apply. The reason feeds the next nightly review, so record the verified facts, not a pleasantry. `claim_insight` marks which run took a finding and clears its card while the insight stays PENDING (the app calls it when handing off, you rarely need it). Prefer `review_insight` over `acknowledge_inbox_item` on a suggestion row: a bare acknowledge records the finding as won't-fix.

The inbox is only the severity-bearing subset of the ``activities`` table, the platform's full event log: every message insert (``MESSAGE_INSERTED``), every run state change (``RUN_QUEUED``, ``RUN_EXECUTED``, ``RUN_WAITING``, ``RUN_COMPLETED``, ``RUN_FAILED``, …), webhook deliveries, and insights. When you need to reconstruct what happened and when (a run that seems stuck, a message that never dispatched, a trigger that did or didn't fire), `query_data` on ``activities`` filtered by ``record_id`` (the run or message id) ordered by ``created_at`` is the debugging timeline, cheaper and often more direct than reading the full trace.

# Webhooks

`list_inbox` is the pull side. Webhooks are the push side. `upsert_webhook(workspace_id, url, …)` subscribes an external URL to your workspace's activity events. The response returns a signing ``secret`` **once**, not retrievable later (not readable through `query_data` either), so store it on the receiving end to verify each delivery's HMAC signature. Narrow what fires with the ``preset_ids``, ``agent_ids``, and ``activity_types`` filter arrays (``activity_types`` takes the same activity type names the inbox uses). Each supplied array replaces the previous one. List your subscriptions (secret redacted) with `list_webhooks`, remove one with `delete_webhook`.

**Reacting to events with an agent.** A subscription may point at an agent's own inbound webhook trigger URL: each matching event then starts a run of that agent with the delivery as its first message, so an agent can admit a contact waiting at a gated channel, re-dispatch a failed run or chase a low balance through the API. Name the watched agents in ``agent_ids``, only the kinds the agent handles in ``activity_types``, and write what to do for each kind into its prompt. Read the ``platform-events`` skill (`get_skill` over the MCP, ``system/skills/platform-events/SKILL.md`` from a run) before wiring one: it carries the delivery shape and, per kind, what a reacting agent can do and which operation settles it.

# API keys

`create_key` mints a durable key for code that outlives this conversation: a deployed app, an external script, a webhook receiver. Pass ``profile_id`` (from `get_me`), a ``name`` saying what it's for, and explicit ``scopes`` (``table:verb`` strings like ``runs:read``, ``runs:create``, or an ``action:`` name like ``action:call_tools``, and a scoped caller can only grant scopes it holds). Each operation in the API document lists what it needs as ``x-scopes``. A scope you pass is stored with the others its operations need, so ``runs:create`` alone is enough to start runs, and a name outside the vocabulary is refused. Omit ``workspace_id`` for a profile key that acts across every workspace the profile belongs to, and ``expires_at`` for a non-expiring key. The response carries ``token`` exactly once (only its hash is stored), so put it where it's needed immediately and never echo it back. `list_keys` and `delete_key` cover rotation and cleanup.

# Billing

Everything runs on workspace credits: one credit is one cent ($0.01) of value.

**Plan and balance.** `billing_status` is the authoritative answer to "what plan is this workspace on" and "how many credits are left": the effective plan, account type, payment method, spendable balance (``credit_total``), run concurrency, ``linked`` (the billing account was originated by another workspace), and ``shared`` (more than one workspace runs on it, so the plan, balance, and purchases are pooled across all of them). Never answer plan or balance questions from `query_data` on ``billings``: the governing row is the one ``workspaces.billing_id`` references, which may belong to another workspace entirely, while ``billings.workspace_id`` only records who originated a row and can match a stale leftover trial.

**The catalog.** `list_plans` lists the subscription plans and the credit packages: each with its price, the credits it includes and, for a plan, the run concurrency it grants. Read it before you name a plan or a price, and pass the ``name`` it returns to `billing_checkout`.

When the balance or the plan is the blocker (a ``low_credit`` inbox row, a run failed on a top-up variant) you can't fix it yourself: generate a URL for the user to open, and let `billing_status` decide which. **Credits are sold only on an active subscription.** While ``plan`` is null the workspace has none, so the link is `billing_checkout(mode="subscription", plan=...)` whatever the user asked to buy: offer the plans `list_plans` returns, mint the checkout for the one the user picks, and the plan's monthly credits are the top-up. A credit package checkout answers 402 there. With a plan, `billing_checkout(mode="payment", package=...)` buys credit packages on top of it (optional ``quantity``), `billing_checkout(mode="subscription", plan=...)` changes the plan (an already-active subscription gets a portal flow URL instead), and `billing_portal` manages the existing subscription and payment methods. Nothing is charged by the calls themselves. Both need an ADMIN profile and the ``action:manage_billing`` scope.

**Cost reporting.** `billing_usage` answers "what did this workspace spend, on what": a time-bucketed series of credits consumed, grouped by cost category (``agent``, ``voice``, ``sms``, ``email``, ``asset_usage``, ``asset_rental``, ``asset_purchase``, ``evaluation``, ``adjustment``). Pass ``start``/``end`` (ISO-8601) and ``bucket_width`` ``1d`` (default) or ``1h``, and add ``group_by=agent_id`` to split by automation, ``asset_id`` to split by asset. Debits only, credit purchases are not in it. Buckets return ``next_cursor``: feed it back as ``cursor``, null when there are no more. Needs an ADMIN profile and the ``ledgers:read`` scope. `get_run_costs` breaks one run down: which models ran and their request counts (the main agent's alongside its sub-agents' and auxiliary calls'), stipend and soft-limit floor, the per-use asset costs the run caused (SMS segments, call telephony, billed to the balance but not part of ``credit_used``), and evaluation spend. Every figure in both reports is a credit count, a cent of value each.

# Removing what you connected

Disconnecting a channel, releasing an asset and removing an integration are row deletes: `delete_data` on ``channels``, ``assets`` or ``integrations`` by ``id``. The platform runs the provider teardown behind each one (a WhatsApp number is deregistered at Meta, a Telegram webhook dropped, a Twilio number or a Supabase project released, a Composio account deleted), so nothing else is needed and nothing else must be done first. Read the links before deleting (``agent_assets``, ``agent_integrations``, ``channels.agent_id``): every agent wired to the row loses that backing at once. An asset release ends its rental and is irreversible (a released database is gone with its data), and a channel delete ends every conversation on it, so confirm with the user and name what disappears. Deleting an agent, a preset or a folder is the same call on its own table.

# Workspaces and members

A workspace is created with `create_workspace`: a ``name``, optionally ``share_billing_with`` (a workspace whose billing you administer, so the new one runs on the same subscription and balance rather than a fresh trial of its own) and ``partner_id`` (a partner organisation you are an admin of, when the workspace is a client of the partner program). You are its ``ADMIN`` on creation. It needs an account and a key across every workspace, since a key pinned to one workspace cannot act in the new one (see **First contact and billing** in `SKILL.md`).

Invite someone with `invite_member` (``workspace_id``, ``email``, ``role`` as ``ADMIN`` or ``MEMBER``): the invitation email goes out with the call, so never call it to "prepare" one. Pending invitations are the rows on ``invitations``, and `delete_data` withdraws one. Members are ``workspace_profiles`` rows (``workspace_id``, ``profile_id``, ``role``): `update_data` changes a role and `delete_data` removes the member, both refused unless you act as a workspace ADMIN or OWNER. Never change your own role or remove yourself, and never touch the OWNER row: those are the workspace owner's calls in the app. `get_me` lists the workspaces the profile belongs to, and ``workspaces.name`` is edited with `update_data` when the user renames one.

# Company record and brain

`upsert_company` keeps the workspace's company record (``name``, ``url``, ``logo``, ``description``, ``sector``, ``size``, and ``data.departments`` / ``data.facts``), written back whenever the user teaches you something about the company. When the company has a brain, the same call carries the settings a member may change under ``data.brain``: ``language`` (``es`` or ``en``), the web research ``agenda`` (topics with ``id``, ``topic``, ``reason`` and ``every``) and the ``forgotten`` pages, merged per key so the pass's own stamps stay. Whether a workspace's runs carry the brain is ``workspaces.data.brain`` (``inject`` puts it in the runs, ``read`` lets the pass read the workspace's conversations), written with `update_data` on ``workspaces``. Which connected tools the pass reads is ``data.brain`` on each ``integrations`` row through `upsert_integration` (``enabled``, ``every``, ``instructions``), and whether a channel's conversations may use it is the channel's ``config.brain``. `run_brain_research` starts the pass on demand. The switch that gives a company a brain is the platform's, not yours: when a workspace has none, say so and move on. The brain's own operations are in `brain.md`.

# Sharing and housekeeping

- **Sharing inside the workspace.** A ``grants`` row shares one agent, preset, folder, channel, integration or asset with one member at ``VIEWER``, ``EDITOR`` or ``MANAGER`` level: `insert_data` with ``workspace_id``, ``table_name`` (``agents``, ``presets``, ``folders``, ``channels``, ``integrations`` or ``assets``), ``record_id``, ``profile_id`` (the member) and ``level``. Only the owner, a workspace admin or a MANAGER grantee may write them. ``public`` on the row itself shares it with the whole workspace instead.
- **Sharing outside.** `mint_agent_share_token(agent_id, open_until)` returns the token behind a public agent link, and a run is shared by setting ``runs.open_until`` with `update_data` (a moment in the future opens the link, ``null`` closes it).
- **Archiving and renaming.** `update_data` setting ``archived_at`` on ``runs`` or ``agents`` archives them, ``null`` restores. Assets are renamed with `upsert_asset` (``id`` plus ``name``), everything else through its ``name`` column.
- **Spending guards.** `billing_recharge_status` / `billing_recharge_update` read and set the auto-recharge knobs (the balance that triggers a top-up, the balance it refills to, the monthly ceiling). They need an ADMIN profile and the ``action:manage_billing`` scope, and they are the user's numbers to set: never pick a ceiling for them. Auto-recharge buys credits, so it runs only on an active subscription: without a plan it never buys, and turning it on answers 402.
- **Phone numbers.** `get_tollfree_verification` / `submit_tollfree_verification` carry a US toll-free number through carrier verification, and `list_number_countries` says per country which number types need a regulatory bundle (see **Assets** in `wiring.md` for bundles).
- **Databases.** `asset_database_options` lists the compute sizes a SUPABASE asset can move to with their credit cost, and `asset_database_resize` applies one.

# Partner tools

When the user belongs to a partner org, a small tool set reads and manages the partner's client workspaces. Every call needs a ``partner_id``: `get_me` returns a ``partners`` list with each org's id and the user's role there. If it's empty, the user isn't a partner member, so don't call these tools. `list_partner_deployments` works for any partner member, and the rest need an ADMIN or OWNER partner role and return 403 otherwise.

The tools: `get_partner_client_usage` (one client workspace's consumption, same shape and parameters as `billing_usage`), `list_partner_deployments` (self-hosted appliance installs: heartbeat, license summary, run telemetry), and the pricing surface (`get_client_premiums`, `set_client_premium`, `set_client_agent_premium`), which reads and sets the client's ``stipend`` / ``multiplier`` / ``soft_limit`` per workspace or per agent (writes need the ``action:manage_partner`` scope, and pricing is only available to partners without a flat commission rate). A client workspace joins the program by carrying the partner's id, passed as ``partner_id`` to `create_workspace` when the partner sets it up. Commission, payout, and cross-client evaluation reporting live in the partner dashboard, not the API.

# Conventions

- Every resource lives under a workspace. Creating one requires ``workspace_id`` **and** ``profile_id`` (your key's profile). A bare ``workspace_id`` is rejected on create.
- Update endpoints take ``id`` and only touch the fields present in the body. Omitting a field leaves it as-is.
- **JSON object fields** (``data``, ``form``, ``recipe``) are *replaced wholesale* when supplied: to change one key, read the current value, merge, and write the whole object back. For ``data`` specifically, `upsert_agent` / `upsert_preset` also accept ``data_patch``, a shallow merge (value = set, ``null`` = delete, omitted = leave) that changes one key without the read-merge-write dance. Don't send ``data`` and ``data_patch`` together. One exception to wholesale-replace: ``recipe`` is never nulled by omission: delete one with ``clear_recipe`` (see **Build and iterate on an agent → Distill a recipe** in `building.md`).
- Nested arrays (``triggers``, ``integration_ids``, ``asset_ids``, ``tool_policies``) are all-or-nothing: omit to leave alone, empty list to clear, populated list to fully replace. To add or edit a single trigger without resending the whole set, use `upsert_trigger` instead (``agent_id`` = the agent id on create, or pass ``id`` to update one).
- `upsert_channel` changes ``public``, ``agent_id``, and ``config`` on update, and requires the channel's *owning* profile. ``config`` carries the channel's runtime behavior: ``delay``/``jitter`` (humanizing reply delay in seconds), ``hours`` (scheduled agent hours: IANA ``tz`` + per-day ``windows``, and outside them conversations park until the next window), ``operator_timeout`` (seconds of operator silence before the agent takes back the conversation), ``access_list`` (sender gating with ``mode`` allow/block and ``entries``), ``reach_external`` (off by default: the conversation's run may only message, cc, or call its own bound contact, and sends naming anyone else are refused, so cc'ing a supervisor or notifying a third party needs it on), ``silent_handoff`` (off by default: when on, ``dispatch_human`` mutes the agent instead of switching the conversation to operator mode. The workspace is notified, the contact gets nothing, and the conversation keeps dispatching on the contact's messages with every channel send refused, so the agent keeps recording while a person talks natively on the account), and ``handoff_notify`` (workspace member profile ids notified per contact message while a handoff holds the conversation, on top of anyone subscribed to the agent or workspace: with nobody at all to notify, the agent's owner is, so a held conversation never goes unwatched). See the tool schema for shapes. Only keys you pass change, and an explicit ``null`` clears one. ``config`` also applies on create, so pass it in the same call that connects the channel. **Working hours, reply pacing and sender gating live here, never in a prompt**: an agent instructed to "only answer between 9 and 18" still dispatches a run for every inbound message and spends a turn on it, while ``hours`` parks the conversation until the window opens. Prefer it over hand-editing ``channels.data`` with `update_data`, which bypasses validation and can clobber the channel's connection internals. To repoint a channel owned by a different profile, set ``channels.agent_id`` via `update_data` (workspace-scoped), but verify the channel is actually wired first (an SMS channel needs an ``asset_id`` binding it to a phone asset, and connected channels carry connection internals in ``data``). A bare row with empty ``data`` and no ``asset_id`` is an orphan no webhook routes to: repointing it changes nothing, and wiring one is done by connecting the channel from the UI, never by hand-editing rows.
- Error responses include a JSON ``detail`` describing what went wrong. When a Composio call fails, ``detail`` carries the upstream message and any suggested fix.
- Vocabulary: ``sandbox`` (not "workspace") for the filesystem the agent works in, ``action`` (not "tool") at the composio/pipedream second level, ``recipe`` (not "flow") for a distilled run.
- The tool schemas over the MCP, and each action's ``--help`` from a run, are the authoritative contract: each operation's description and parameter shapes travel with the operation itself. This guidance is the map, not the spec. When the two disagree, trust the schema or the help text.

# Worked examples: from a request to platform actions

How a user's ask (in their vocabulary) decomposes into platform actions. Illustrative, not exhaustive: the decision rules live in the files above.

**"Every Monday, email me a sales summary."** Recurring and unattended → an agent with a trigger. (1) `find_providers` for the data source, and if it isn't connected, request the connection rather than guessing credentials. (2) `upsert_agent`: prompt per **Writing agent prompts** in `building.md`, ``integration_ids``, a user-facing ``description``, a system ``preset_id``. (3) ``triggers=[{cron "0 9 * * 1", timezone}]``. (4) Announce, then test with `start_run` and read `get_run_trace`. Not: running it by hand every Monday, adding a ``form`` (nothing to fill), or guessing a ``trigger_slug`` without `find_providers`.

**"Download this portal's invoices for me, now."** One-off → a bare `start_run` with the whole brief in ``text`` (browsing included), then deliver the files from the settled status. Offer to save it as an agent only if it looks recurring. Not: building an agent first, which leaves persistent clutter for a single execution.

**"Re-engage my old clients over WhatsApp and get them to book appointments. Their data is scattered across spreadsheets and old exports."** A multi-piece build like this is what **packages** are for. The `whatsapp-reengagement` package carries the full blueprint: a shared database asset at the center, one preset carrying the shared persona, one thin conversational agent per number, cron-fired launcher agents doing the outreach, and a sync agent closing the loop. `get_package` it and follow its build order rather than improvising the decomposition. Not: one giant agent doing outreach, conversation, and sync, the client list pasted into prompts instead of the database, or all the volume through one number.

**"Set my client up: they need an agent answering their WhatsApp."** A builder working for a client → a workspace of the client's own. (1) `create_workspace` with the client's name, sharing your billing when the user says you carry the subscription. (2) Build the agent in it and connect the channel there. (3) `invite_member` with the client's email as ``ADMIN`` once it runs (invitations grant ``ADMIN`` or ``MEMBER`` only). (4) When the client pays for themselves, hand them a `billing_checkout` link for their workspace. Not: building in the user's own workspace and moving it later, or inviting the client before the first demonstrated run.
