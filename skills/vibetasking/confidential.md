# Keeping data out of the AI's reach

This file applies when the person asks that some of what an integration answers never reaches the AI (an agent, or you), or when a commitment they made says so: a school's student records, patients' files, a client's data under contract. Every other connection takes the usual path, the service's integration when `list_providers` offers one, otherwise a credential the service issues (see **Secrets and credentials** in `operations.md`) used from a run, or the browser. Offer what follows only when the person's need is that one.

## Protected fields

An integration with protected fields answers its tools through rules, field by field: a field is kept, turned into a code like ``AL-7Q3K...`` that always stands for the same value, or shown as its year, and a field with no rule is left out and named under ``withheld_fields``. Pass a code back as an argument of the same integration's tools and the call uses its value, so count, group and look up records by their codes and work with them as they are. `list_integration_fields` reads the rules a page of tools at a time, each in ``data`` with its ``tool``, by dotted path (``[]`` a list's items, ``{}`` a map's entries, ``$`` the whole answer). `update_integration_fields` changes them: ``protected`` switches the rules on or off, and ``rules`` maps a tool to its paths, each to ``{"rule": "CODE", "prefix": "AL"}`` or a rule alone, ``"KEEP"``, ``"YEAR"`` or null to take it away. Hiding more applies at once, and reaches a run already working from its next turn. Showing more (protection off, a field kept or shown as its year where it was coded or left out) is the person's to approve, and the call waits for them. When a field the work needs is withheld, tell the person which and let them decide.

## Custom integrations

When the data that must stay out comes from an API no provider offers (a client's SOAP service, an internal REST backend, anything with a Swagger file, a WSDL, a Postman collection or a cURL example), describe the API as a **CUSTOM** integration, so its answers pass the protected fields' rules like any integration's. A **CUSTOM** integration turns an API into tools: each operation it describes (a request with its arguments) becomes a tool its agents call, and the platform signs each request with the integration's credentials, which no agent ever holds.

1. **Describe it.** When the user has a description of the API, `preview_custom_operations` with its ``kind`` (``openapi`` for OpenAPI or Swagger, ``wsdl``, ``postman`` or ``curl``) and the text as ``source`` or a public address as ``url`` answers the ``operations``, the ``base_url``, the ``session`` (a sign in the operations reuse), the ``credentials`` they reference and what it ``skipped``, saving nothing. Keep only the operations the user's work needs, each with a ``description`` that says when to call it, and keep each one's ``answer`` as previewed: its ``fields`` let the person rule what reaches the AI before any call. Without a description, write the operations yourself: a ``name`` (lowercase, underscores), a ``description``, ``arguments`` (a JSON schema of type object), a ``request`` (``method``, ``path`` relative to the base URL, ``headers``, ``query``, a ``body`` with its ``format`` ``json``, ``xml``, ``form`` or ``text`` and its ``template``) and an ``answer`` (``format`` ``json``, ``xml``, ``csv``, ``text`` or ``binary``, and a dotted ``root`` naming the part worth answering). A template references ``{{args.<name>}}``, ``{{credential.<name>}}`` and, with a session, ``{{session.token}}``, and the platform escapes every value for where it lands. An operation that only reads is called freely, one that writes asks for approval where the run's settings ask.
2. **Create it.** `create_integration` with ``type`` ``CUSTOM`` and ``config.custom`` holding ``name``, an optional emoji ``icon``, ``base_url`` and the ``operations`` (and the ``session`` when there is one). `update_integration` with ``config.custom`` replaces the whole description.
3. **Have the person enter the credentials.** Never ask for a key, a password, a token or a certificate in the conversation, and never put one in a template. Tell the person which credentials the operations name and send them to the integration's page in the app, under Integrations, where they enter each value, how it is used (a value, a key the platform makes a token from, a client certificate or a proxy) and the hosts it may be sent to, the base URL's host unless they name others. A credential is only ever sent to its hosts.
4. **Try it and link it.** `list_toolkit_tools` with ``CUSTOM`` and the integration's ``integration_id`` lists its operations as tools. `call_toolkit_tool` with the toolkit ``CUSTOM``, the integration's ``integration_id``, the operation's name as the tool and its arguments runs one operation outside any run, the way to check it answers before an agent relies on it. Link the integration to the agent like any other. Inside a run the tools are named after the integration, ``<name>_<operation>``, on the shell under ``custom_api``. When a call answers that the credentials were refused, the integration needs them entered again on its page, so tell the person.
