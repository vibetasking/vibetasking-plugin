# Reading resources

Every platform resource is read through its own operations, scoped to your workspace and your key, and every one answers the same shapes.

- **A list pages by cursor.** `list_*` answers ``{"object": "list", "data": [...], "next_cursor": ...}``, newest first, at most ``limit`` rows (50 by default, 200 at most). While ``next_cursor`` is not null, pass it back as ``cursor`` for the next page. There is no total: page until ``next_cursor`` comes back null.
- **Filters are named per resource.** Each list takes the filters its tool schema lists, on indexed fields only: the field's name for equality (``agent_id=...``), a comma list for any of (``state=FAILED,WAITING``), ``null`` for absent, and on a timestamp the suffixes ``_gte``, ``_gt``, ``_lte`` and ``_lt`` with the name losing its ``_at`` (``created_gte=2026-10-01T00:00:00Z``). ``q`` searches the resource's text fields where it has any. ``sort`` takes a field the list sorts by, with a leading ``-`` for descending. A filter the list does not declare is refused, naming the ones it takes.
- **A get reads in full.** A list and a write answer an unbounded text (a prompt, a run's result, a message's content) as ``{chars, sha256}``, and `get_*` answers it in full. Compare a write's descriptor with what you sent instead of reading a large text back.
- **`expand` embeds a related row** one level deep, where the resource declares it: `get_agent` with ``expand=preset`` or ``expand=folder``, `get_run` with ``expand=agent``. A related row you cannot see comes back null.
- **Empty result vs. no access.** A row that exists but that your key cannot see answers 404, the same as one that does not exist, and a list leaves it out: that's scoping, not absence. A row you see but may not change answers 403 on the write.
- **Writes are merges.** An `update_*` changes only the fields it is sent: an object merges key by key, ``null`` clears a field that may be cleared, an array is replaced whole. A relation several writers change is its own sub resource, added and removed one at a time (`add_agent_integration`, `remove_agent_integration`). Send ``If-Match`` with the ``etag`` you read to refuse a write when the row moved since (412).
- **A create or a start takes an ``Idempotency-Key``.** A repeat of the same key and body within a day answers the first result without doing the work again. A run's own calls send theirs on their own.
- **Errors share one envelope:** ``{"error": {"code", "message", "status", "param", ...}}``. ``MISSING_SCOPE`` names the scopes in ``details.scopes``, ``VALIDATION_ERROR`` lists each field in ``errors``, and ``param`` names the argument a ``INVALID_REQUEST`` or a ``NOT_FOUND`` is about. ``request_id`` names the request: give it to the user when a failure is the platform's to look into, since support opens the request by it.
- **The workspace is automatic.** A list or a create takes an optional ``workspace_id``. A key pinned to one workspace leaves it out, and a key across every workspace names the one to act in.

From a run's shell the same operations read as ``vibetasking list_runs --json '{"state": "RUNNING", "limit": 20}'`` and ``vibetasking get_agent --json '{"agent_id": "...", "expand": "preset"}'``, each taking the ``--json`` body its ``--help`` describes.

## Reaching an asset's own database

To read or write a **SUPABASE asset's own project** (the leads/CRM database provisioned for an automation) rather than the platform's resources, read with `read_asset_api` and write with `call_asset_api`, each taking the asset's ``asset_id``. They attach the provider credentials, so you never handle tokens. Needs the ``action:proxy_assets`` scope.

- **Table CRUD → PostgREST data-plane** (recommended). ``path="rest/v1/<table>"``. Reads: `read_asset_api` with ``query`` params (``select``, filters like ``column=eq.x`` / ``column=in.(a,b)``, ``order``), **capped at 1000 rows and silent about it**: page ``limit``/``offset`` until a page comes back short, and take counts and aggregates from the SQL path below rather than adding up rows. An app on the project hits it too, through ``@supabase/supabase-js``. Writes: `call_asset_api` with ``method="PATCH"`` / ``"POST"`` / ``"DELETE"`` and a JSON ``body`` of the new values, plus header ``Prefer: return=representation`` to get the affected rows back.
- **Arbitrary SQL → Management API.** `call_asset_api` with ``path="v1/projects/{project_ref}/database/query"``, ``method="POST"``, ``body={"query": "<one statement>"}``, a ``select`` included. ``{project_ref}`` is the asset's ``reference``, validated so you can't target another project. Use for DDL, joins, counts and aggregates, one statement per call.
- **The project's keys and password stay with people.** Its API keys and its database password are not reachable through either operation (403). When the user wants them, for their own app, a database client or another tool, point them to the database's settings in the app: its owner or a workspace admin reveals them there, and rotates them if they leak.
