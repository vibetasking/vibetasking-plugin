# Reading and writing data

The Data tools run against the *platform* database through PostgREST, scoped to your workspace and your key.

- **`query_data` is PostgREST.** ``select`` takes projection, JSON paths, and embeds, e.g. ``id,name``, ``status:data->>delivery_status``, ``code:data->error->>code``, ``agents(id,name)``. ``filters`` is a list of ``{column, op, value}`` (ops: ``eq, neq, gt, gte, lt, lte, like, ilike, in, is``. For ``in`` pass a comma-separated ``value``, for ``is`` pass ``null``/``true``/``false``). ``or_filters`` are OR-combined among themselves, then AND-ed with ``filters``. ``order``/``limit``/``offset`` work as expected, ``limit`` defaulting to 100 and capping at 1000. Project only the keys you need: a whole ``data`` column runs hundreds of KB per row, so a wide page fails at 413. ``ilike`` on it never uses an index and times out. Page a ``created_at`` filter forward, as ``offset`` costs every row skipped.
- **Filter on indexed columns.** Primary and foreign keys (``id``, ``run_id``, ``agent_id``, …) are fast. An un-indexed JSON path across a whole table (``data->>delivery_status`` with nothing else narrowing it) can hit the statement timeout, so scope it first (by ``run_id`` or another key) and read in batches.
- **Empty result vs. no access.** Reads are scoped to your workspace, profile, and key scopes. A row that exists but belongs to a different profile (this is common for ``presets`` and ``channels``) can come back empty: that's scoping, not absence. Read a preset's effective prompt through `get_run_trace`, and mutate such rows through the dedicated `upsert_*` / `update_data` paths rather than expecting them in a `query_data` result.
- **JSON writes:** when you change a JSON object field, write the whole object back (see **Conventions** in `operations.md`).
- **`call_rpc`** invokes a Postgres function PostgREST exposes (``function`` name plus ``args`` keyed by parameter name), under the same scoping.
- **The workspace is automatic.** These operations accept an optional ``workspace_id``. A key pinned to one workspace never sets it (pointing it at another workspace is rejected), and a key across every workspace names the one to read.
- **`update_data` and `delete_data` require at least one filter**, so no write is ever unbounded.

From a run's shell the same six actions read as ``vibetasking describe_schema --json '{"table": "runs"}'``, ``vibetasking query_data --json '{"table": "runs", "filters": [{"column": "state", "op": "eq", "value": "RUNNING"}], "select": "id,name,state,created_at", "order": "created_at.desc", "limit": 20}'`` and their ``insert_data``, ``update_data``, ``delete_data`` and ``call_rpc`` siblings, each taking the same ``--json`` body the schema describes.

## Reaching an asset's own database

To read or write a **SUPABASE asset's own project** (the leads/CRM database provisioned for an automation) rather than the platform database, use `asset_proxy_call` with the asset's ``asset_id``. It attaches the provider credentials, so you never handle tokens. Needs the ``action:proxy_assets`` scope.

- **Table CRUD → PostgREST data-plane** (recommended). ``path="rest/v1/<table>"``. Reads: ``method="GET"`` with ``query`` params (``select``, filters like ``column=eq.x`` / ``column=in.(a,b)``, ``order``), **capped at 1000 rows and silent about it**: page ``limit``/``offset`` until a page comes back short, and take counts and aggregates from the SQL path below rather than adding up rows. An app on the project hits it too, through ``@supabase/supabase-js``. Writes: ``method="PATCH"`` / ``"POST"`` / ``"DELETE"`` with a JSON ``body`` of the new values, plus header ``Prefer: return=representation`` to get the affected rows back.
- **Arbitrary SQL → Management API.** ``path="v1/projects/{project_ref}/database/query"``, ``method="POST"``, ``body={"query": "<one statement>"}``. ``{project_ref}`` is the ``reference`` column on the asset's row, validated so you can't target another project. Use for DDL, joins, counts and aggregates, one statement per call.
- **The project's keys and password stay with people.** Its API keys and its database password are not reachable through `asset_proxy_call` (403). When the user wants them, for their own app, a database client or another tool, point them to the database's settings in the app: its owner or a workspace admin reveals them there, and rotates them if they leak.
