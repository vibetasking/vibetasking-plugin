# Presets

A **preset** is a reusable bundle of model, reasoning, language, fallback, and integration defaults. Agents attach a preset via ``agent.preset_id`` and inherit its ``data``. Most workspaces use **system presets** (rows in ``presets`` with ``workspace_id IS NULL``). An agent with no ``preset_id`` reads the workspace's default preset (``workspaces.preset_id``), and the platform default, which is what the ``Ultra`` tier carries, when the workspace sets none (see **Choosing a tier** below). Don't put ``data.model`` on the agent itself unless you have a specific override. Let it cascade from the preset so multiple agents can share the same model setup.

The preset's own ``prompt`` is shared instructions applied under every agent that attaches it. Put shared persona and behaviour on the preset and keep per-agent specifics (identity, links, the exact task) on the agent's ``prompt``. Several agents can then share one preset and you edit the common parts once.

# Run configuration

Model choice and runtime behaviour live in the ``data`` object that presets, agents, and runs all carry (the same shape on each). The authoritative list of keys, with a description of what each does, is the ``data`` field on the `upsert_agent`, `upsert_preset`, and `start_run` contracts: the tool schemas over the MCP, the actions' ``vibetasking <action> --help`` from a run. Read it there rather than guessing. On these tools an unknown key is rejected outright, but a raw `update_data` write accepts anything, so a typo there fails silently.

Precedence runs preset → agent → run, last writer wins. A key set on the run's ``data`` overrides the same key on the agent, which overrides the preset, and anything you leave unset falls back to a platform default. So put shared defaults on the preset and override per-agent (or per-run) only what differs. To change one key without resending the whole object (and dropping the rest), use ``data_patch`` (see **Conventions** in `operations.md`).

The knobs you reach for most:

- **Model.** ``model`` is a provider-prefixed identifier (e.g. ``google-gla:gemini-3.8-flash``). Pick it from the catalog rather than guessing an identifier: `list_models` returns every available model with pricing and capability metadata, `get_model` one model's detail. ``fallback_models`` is an ordered list tried in turn when the primary errors. ``reasoning_effort`` buys deeper analysis at higher cost and latency on models that support it. ``timeout`` caps each model request. A CLAUDE run, the default engine, reads its model and effort from ``claude`` instead (``model`` in the vendor's own naming, such as ``claude-opus-5-5``, and ``effort``), and a CODEX run from ``codex``.
- **Choosing a tier.** A tier is a preset, not a model identifier you carry in your head. Each tier is a system preset (a ``presets`` row with ``workspace_id is null``) whose ``data`` holds the model, ``reasoning_effort`` and relative ``cost`` that tier means right now, alongside the label and description the user sees. A ``discount`` is the percent off that ``cost``, so compare tiers on the discounted price. A tier on the CLAUDE engine carries its model and effort under ``claude`` instead of ``model`` and ``reasoning_effort``. Read them with `query_data` before you name a tier or attach one, offer only the rows flagged ``data.featured``, and never a ``data.hidden`` row. They are ``Ultra``, ``Balanced`` and ``Efficient``.
  - **Switching tier is a ``preset_id`` change.** Point ``preset_id`` at that tier's preset with `upsert_agent` and leave ``model`` out of the agent's own ``data``. A model written there pins the agent to today's identifier and shadows the preset from then on, so it stops following the tier the user picked. When the ask is a tier ("ponlo en eficiente") and the agent's current preset is a system preset or none, ``preset_id`` is the whole edit.
  - **A workspace preset is more than a tier.** A preset the workspace built (``workspace_id`` set) can carry a ``prompt``, artifact files, integrations, assets and vault items its agents depend on, so repointing ``preset_id`` takes those away along with the model. Read the preset row, its links and `list_files_in_entity` first. When any of it is there, carry it onto each agent (append the prompt to the agent's own, upload the files and link the backings to the agent, see `agents.md`, and `operations.md` for vault items) before you switch, and tell the user what moved.
  - **``Ultra`` is the default and the only tier you attach on your own judgment.** It is the most capable tier and, discounted, also the cheapest, so there is generally no reason to pick another. A new agent needs no tier of its own: left without ``preset_id`` it runs on the workspace's default preset, and on the platform default, which is what ``Ultra`` carries, when the workspace sets none.
  - **``Balanced`` and ``Efficient`` only when they are asked for.** Attach one when the user names that tier, never on your own initiative, whatever the task looks like. Neither saves credits: ``Ultra`` already costs least, so "make it cheap" with no tier or model named means ``Ultra``.
  - **An unset model is already the default, not a stronger one.** A run with no ``model`` on the run, its agent or the preset it reads executes on that preset's configuration, and with no preset anywhere on the platform default, which is what ``Ultra`` carries. A ``null`` there is an answer rather than a gap: read it as the default, not as a tier inferred from how hard or how costly the task looked.
  - **Name a run's model from a record.** `get_run_costs` lists every model that billed the run with its request counts, and that covers its sub-agents and auxiliary calls alongside the main agent, so read it together with the run's own ``model`` and ``preset_id`` to say which one the agent ran on. Cost questions turn on this: attributing a bill to a tier the run never used sends the user to change the wrong thing.
  - **A sub-agent specialist carries its own model.** A dispatch with ``specialist`` set to ``extractor``, ``browser`` or ``viewer`` runs on the model this deployment pins to that specialist, and that pin sits above the agent's ``model`` and above the ``sub.default`` group, so only the specialist's own group (``sub.extractor``, ``sub.browser``, ``sub.viewer``) re-points it. `list_models` names each pinned model under ``roles``.

  Setting a model yourself is the exception: a model the user expressly named, written under the key the agent's engine reads (``model`` on VIBETASKING, ``claude.model`` on CLAUDE, ``codex.model`` on CODEX), or a ``sub.*`` override. Read the identifier off the preset row or `list_models` rather than recalling one, and never substitute a bargain model from the catalog to save credits, no GPT mini, Haiku, DeepSeek Flash, or other off-list model the user did not ask for.
- **Cost.** ``credit_limit`` is a per-run ceiling that halts the run before it exceeds the amount. Set it only when the user asks for a spending cap, and never change a cap the user set: a guessed ceiling stops the task midway with nothing delivered. It counts everything the run has ever spent, so on a channel agent, whose conversation with each contact is one run that never ends, it is a lifetime cap per contact: pair it with ``daily_reset: true`` there, which makes it a daily ceiling instead. Turning off ``planning``, ``describe_task``, and ``describe_events`` trims spend on simple tasks.
- **One at a time.** ``single_flight`` (agent only) serializes an agent's own starts: a start that lands while one of its runs is still in flight returns that run's id with ``skipped: true`` instead of starting a second. Set it on any agent whose runs share state (a launcher working a queue, a sweeper walking a list) where two overlapping runs would claim the same rows. The platform takes the lock, so the prompt must not check for a sibling run itself: reading ``runs`` and deciding is a race that sometimes lets both through. It does nothing on a channel-attached agent, which keeps one run per contact on purpose.
- **Output shape.** ``output_schema`` is a JSON schema the final result must validate against, and the validated value comes back as ``run.result``. Set it when you need a machine-readable answer instead of prose.
- **Behaviour.** ``allow_connections`` (whether the agent may ask for a new integration or credential, see **Connections on a channel agent** in `wiring.md`: on by default only on a run a workspace member owns, so off on every channel conversation until you set it), ``approval`` (require human sign-off before each tool call), ``language`` (the language of the platform's own notices around the run). ``interactive`` (whether a person is reachable in the run's conversation, which is what lets the agent ask anything of anyone). Left unset it follows the run's shape: a channel conversation is interactive, a scheduled run or one started by an API key is not, and a delegated run inherits its parent. Set it to make a scheduled run reach its owner, or to run a conversation unattended.
