# Presets

A **preset** is a reusable bundle of model, language, and integration defaults. Agents attach a preset via their ``preset_id`` and inherit its ``config``. Most workspaces use the platform's presets, the ones `list_presets` answers with a null ``workspace_id``. An agent with no ``preset_id`` reads the workspace's default preset, and the platform's when the workspace picks none, the one `list_presets` marks with ``tier.default`` (see **Choosing a tier** below). The default is `get_workspace`'s ``preset_id``, which an admin changes with `update_workspace`. Don't put ``models`` in the agent's own ``config`` unless you have a specific override. Let it cascade from the preset so multiple agents can share the same model setup.

The preset's own ``prompt`` is shared instructions applied under every agent that attaches it. Put shared persona and behaviour on the preset and keep per-agent specifics (identity, links, the exact task) on the agent's ``prompt``. Several agents can then share one preset and you edit the common parts once.

**A preset you create replaces the tier for its agents.** A run reads one preset, so an agent on yours no longer follows the workspace's default tier, and with no ``models`` it runs on the workspace's own configuration, else on what the platform's default tier runs. Copy into the new preset the ``config.models`` of the tier its agents should run on, as `list_presets` answers it: the workspace's default unless the user names one. Tell the user which tier it is.

# Run configuration

Model choice and runtime behaviour live in the ``config`` object that presets, agents, and runs all carry (the same shape on each). The authoritative list of keys, with a description of what each does, is the ``config`` field on the `create_agent`, `create_preset` and `create_run` contracts: the tool schemas over the MCP, the actions' ``vibetasking <action> --help`` from a run. Read it there rather than guessing: an unknown key is rejected outright.

Precedence runs preset → agent → run, last writer wins. A key set on the run's ``config`` overrides the same key on the agent, which overrides the preset, and anything you leave unset falls back to a platform default. ``models`` layers per purpose instead (below). So put shared defaults on the preset and override per-agent (or per-run) only what differs. An `update_agent` or `update_preset` merges its ``config`` key by key, inside ``models`` purpose by purpose and inside ``network`` host by host, so send only what you change, and a ``null`` removes it.

The knobs you reach for most:

- **Models.** ``models`` holds, per purpose, what that purpose runs on: ``turn`` for the agent's own turns, ``worker`` for the platform's small calls around the run, ``sub`` for a dispatched sub-agent, ``browser``, ``viewer`` and ``extractor`` for each specialist, and the media, decision and call purposes `get_purposes` lists. A purpose takes ``entries``, tried in order, the first that can run running and the rest its fallbacks, each a ``provider`` (``automatic``, the default, which runs the model on the workspace's own accounts that serve it and then on VibeTasking, ``vibetasking`` for VibeTasking alone, the id of one of the workspace's own accounts or subscriptions `get_purposes` lists under ``providers`` for that account alone, or ``voice-loop`` on a call), a ``model`` from the catalog (`list_models`, `get_model`, never an identifier from memory) and its ``settings`` (``effort``, ``verbosity``, ``temperature``), which live on the entry alone: to change the effort of the models a lower layer names, name those entries with the new effort, as `get_purposes` lists them under the purpose's ``options``. The nearest layer that names a purpose's entries wins, and a purpose no layer sets runs on the workspace's configuration, else on the platform's. No entry names an engine or one of VibeTasking's own providers: what serves the model decides where a turn runs. `list_purpose_choices` lists what each provider of the workspace could run a purpose on. ``timeout`` caps each model request.
- **Choosing a tier.** A tier is a preset, not a model identifier you carry in your head. Each tier is one of the platform's presets whose ``config.models`` holds what that tier means right now, and whose ``tier`` holds what the user sees: its relative ``cost`` before what it takes off for a workspace, ``featured``, ``hidden``, its ``label`` badge and whether it is the platform's ``default``. What each tier costs this workspace is in `get_purposes` under ``tiers``, one entry per preset (``preset_id``): ``on`` is who serves its agent turn for the workspace (``vibetasking`` in credits, ``own`` on an account or a subscription of the workspace's own, null where nothing it names can run), ``discount`` the percent its agent turn costs less than the model's standard price, null where it costs the same, and ``relative`` what its agent turn costs against the cheapest of the platform's presets, which reads 1, its discount counted. An agent can pay less than the rest of its workspace (one that keeps the price it started on), so for one agent pass its ``agent_id`` to `get_purposes`, and ``tiers`` then say what each tier costs that agent. Compare tiers on ``relative``. Read them with `list_presets` before you name a tier or attach one, offer only the ones whose ``tier.featured`` is true, and never a ``tier.hidden`` one. They are ``Ultra``, ``Balanced`` and ``Efficient``.
  - **Switching tier is a ``preset_id`` change.** Point ``preset_id`` at that tier's preset with `update_agent` and leave ``models`` out of the agent's own ``config``. A ``turn`` written there pins the agent to today's identifier and shadows the preset from then on, so it stops following the tier the user picked. When the ask is a tier ("ponlo en eficiente") and the agent's current preset is one of the platform's or none, ``preset_id`` is the whole edit.
  - **A workspace preset is more than a tier.** A preset the workspace built (``workspace_id`` set) can carry a ``prompt``, artifact files, integrations, assets and vault items its agents depend on, so repointing ``preset_id`` takes those away along with the model. Read the preset with `get_preset` (its own disk is among its ``mounts``), its links (`list_preset_integrations`, `list_preset_assets`, `list_preset_vault_items`) and `list_files` on its disk first. When any of it is there, carry it onto each agent (append the prompt to the agent's own, write the files to the agent's disk and link the backings to the agent, see `agents.md`, and `operations.md` for vault items) before you switch, and tell the user what moved.
  - **The default tier is the one for a new agent.** Left without ``preset_id``, an agent runs on the workspace's default preset, else on the platform's, the one whose ``tier.default`` is true. A new agent needs no tier of its own, and no other tier is attached on your own judgment.
  - **``Ultra`` is the most capable tier, and the most expensive at its standard price.** Attach it when the user asks for it. When an agent keeps failing at work its tier is too light for (a judgement call it gets wrong, a long document it loses track of), propose ``Ultra`` with what it costs against the agent's tier, and switch once the user agrees.
  - **Cheaper or faster replies mean a lighter tier, proposed with its price.** When the user wants an agent to cost less or answer faster without naming a tier or a model, propose the next lighter featured tier that costs that agent less, passing over one that does not: ``Balanced`` from ``Ultra``, ``Efficient`` from ``Balanced``. ``tier.cost`` is the price the user sees before what a tier takes off, and ``relative`` in ``tiers`` read for the agent what each tier costs it, so a large ``discount`` can make a heavier tier cost it less than a lighter one, and you tell the user its tier is the cheaper of the two. Say what a switch saves from ``relative`` (3 to 1 is two thirds less), never from the ``$`` signs. An agent turn ``on`` ``own`` bills the workspace's own account rather than credits, so a lighter tier saves no credits there, and you say so. ``Efficient`` (``tier.label`` ``fast``) is the cheapest and the quickest, for simple tasks where some margin of error is acceptable: name that tradeoff, and switch once the user agrees. Cost has its own levers besides the tier (**Cost** below). A voice agent's pace on a call is its call provider's and its speaking instructions', not its tier's (see `wiring.md`).
  - **An unset model runs on the platform's default.** A run with no ``turn`` on the run, its agent or the preset it reads executes on the workspace's configuration, else on the platform's, which holds what the platform's default tier runs. A ``null`` there is an answer rather than a gap: read it as that configuration, not as a tier inferred from how hard or how costly the task looked.
  - **Name a run's model from a record.** `get_run_costs` lists every model that billed the run with its request counts, and that covers its sub-agents and auxiliary calls alongside the main agent, so read it together with the run's ``engine`` and ``preset_id`` to say which one the agent ran on. Cost questions turn on this: attributing a bill to a tier the run never used sends the user to change the wrong thing.
  - **A sub-agent specialist carries its own model.** A dispatch with ``specialist`` set to ``extractor``, ``browser`` or ``viewer`` runs on that specialist's own purpose, not on ``sub``, so only ``models.extractor``, ``models.browser`` or ``models.viewer`` re-points it. `list_models` names under ``roles`` the purposes the platform runs each model on.
  - **A model already set is someone's choice.** A ``models`` entry on an agent or a preset was put there on purpose, often to run a purpose on an account of the workspace's own, which bills that account instead of credits. Keep it through every other edit, and change or remove it only when the user asks for that, or for a tier its ``turn`` would shadow. When another model looks better for the task, tell the user what the purpose runs on now, what it would run on instead and what each costs (`get_purposes`), and let them decide.

  Setting a model yourself is the exception: the tier a preset you create copies (**A preset you create** above), or a model the user expressly named, written as the entry of the purpose it is for (``turn`` for the agent itself). Read the identifier off the preset, `list_purpose_choices` or `list_models` rather than recalling one, and never substitute a cheaper model the user did not ask for to save credits. An entry that names exactly what the layers below already run for that purpose is not stored, since the agent runs it already and keeps following them, so reading the agent back shows no entry there: that is the write having landed.
- **Cost.** ``credit_limit`` is a per-run ceiling that halts the run before it exceeds the amount. Set it only when the user asks for a spending cap, and change a cap the user set only when they ask (raising or lifting it waits on their approval, see **A change a person makes** below): a guessed ceiling stops the task midway with nothing delivered. It counts everything the run has ever spent, so on a channel agent, whose conversation with each contact is one run that never ends, it is a lifetime cap per contact: pair it with ``daily_reset: true`` there, which makes it a daily ceiling instead, and a conversation it paused carries on by itself at midnight UTC. ``daily_credit_limit`` (agent or preset) is a limit on the agent's whole day, or on a preset's runs with no agent, counted in UTC: once its runs spent it, each of them waits on a card, before its turn or during one, and carries on by itself at midnight UTC unless a person continues it or raises the limit sooner. Set it when the user wants an agent's daily spend bounded, an unattended one above all. Turning off ``planning``, ``describe_task``, and ``describe_events`` trims spend on simple tasks.
- **One at a time.** ``single_flight`` (agent only) serializes an agent's own starts: a start that lands while one of its runs is still in flight answers that run instead of starting a second. Set it on any agent whose runs share state (a launcher working a queue, a sweeper walking a list) where two overlapping runs would claim the same rows. The platform takes the lock, so the prompt must not check for a sibling run itself: listing runs and deciding is a race that sometimes lets both through. It does nothing on a channel-attached agent, which keeps one run per contact on purpose.
- **Memory.** ``memory`` is what a run does with the notes its agent's runs keep at ``memory/``: ``WRITE`` (the default) keeps and reads them, ``READ`` reads them and adds none, ``OFF`` mounts none. Set it on the agent when the user wants it to stop learning from its runs or to keep what it has without adding more. The person's own Coordinator memory follows the workspace's Coordinator preset, which they switch in the Coordinator's settings.
- **Output shape.** ``output_schema`` is a JSON schema the final result must validate against, and the validated fields come back as the run's ``output``, beside its ``result`` text. Set it when you need a machine-readable answer instead of prose.
- **Behaviour.** ``allow_connections`` (whether the agent may ask for a new integration, asset, channel or credential mid run, for that run alone, see **Connections on a channel agent** in `wiring.md`: on by default only in a Coordinator conversation, so any other run reports what it lacks as its blocker until you set it, while a run a workspace member owns can always ask to reconnect what it already holds), ``approval_mode`` (when a person confirms before the agent acts, loosest first: ``allow`` asks nothing beyond the resources' own permissions, ``auto`` has an AI review each write and ask only about what it doubts, ``edits`` lets file edits go ahead and asks about every other write, ``ask`` asks about every write, and ``read_only`` lets nothing write, a stricter layer never loosened by a looser one and a resource's rule that asks its owner still asking the owner),  ``language`` (the language of the platform's own notices around the run). ``interactive`` (whether a person is reachable in the run's conversation, which is what lets the agent ask anything of anyone). Left unset it follows the run's shape: a channel conversation is interactive, a scheduled run or one started by an API key is not, and a delegated run inherits its parent. Set it to make a scheduled run reach its owner, or to run a conversation unattended.
- **A change a person makes.** Some changes run only as a person: lowering a safeguard (loosening ``approval_mode``, raising or lifting ``credit_limit`` or ``daily_credit_limit``, turning ``daily_reset`` on, exempting a trigger from the daily budget (``budget_exempt``), widening what a run reaches or easing or lifting a tool rule of an integration, a channel, an asset or a device, deleting an agent or a preset that holds one), lowering, archiving, deleting or changing a case that holds runs back or tells someone, or saying one of its flags was mistaken, lifting a standing approval that asks or refuses, reverting a change into any of these, and the workspace's owner settings (``supervision``, its approval mode, Knowledge, who manages credentials, how long it keeps records). When the user wants one, or one you set up no longer serves (a case you added for a test), make the call. It waits on an approval card that shows the user exactly what it changes, or on their own line you ask them in the conversation, and once they approve it runs as them, that once. It still takes someone who may make it, an owner for an owner's setting.

# Where the workspace's AI runs

Every AI call runs on a purpose's entries. An API account of the workspace's own serves every ``automatic`` entry of a model it serves ahead of VibeTasking, your own turns included, and alone every entry naming it. A Claude Code or Codex subscription serves those entries only for the runs it is switched on for: a member's own their Coordinator and Supervisors, and the workspace's what its owner switches on, the Coordinator and Supervisors of members without their own, the Curator, and on the Enterprise plan the workspace's agents. `get_purposes` answers, for every purpose, what the platform, the workspace and the preset and agent you name (``preset_id``, ``agent_id``) set, and its ``options``: each entry as it runs for the workspace, in order, with a ``reason`` where it cannot run (``off``, its provider switched off, ``gone``, ``refused``, ``busy``, its provider at its limits for now, ``role``, a subscription not switched on for these runs, ``unserved``, ``unknown``, a model the catalog does not know for the purpose, or ``unpriced``, a model no price covers, which only an account of the workspace's own may serve). Its ``providers`` list the workspace's own accounts and subscriptions, which their provider bills instead of credits, and the platform's, each with whether it is ``on``. A call one of the workspace's own accounts serves bills that account for its model and a share of the model's API price in credits, and what VibeTasking runs around it bills credits too: the run's sandbox, the platform's calls VibeTasking serves, and the model on a turn the account cannot serve under ``automatic``. Read it before you say which model or provider a purpose runs on or why one is off, and before you build an agent around a purpose that is off. `list_accounts` names each account a ``provider`` id points at.

- **Accounts, providers and the workspace's own configuration are a person's.** Adding, changing or removing an account, switching one of the platform's providers off, and setting what a purpose runs on for the whole workspace are done by a person in the app's settings, under AI providers (see **The workspace's AI providers** in `app.md`). Point the user there. An agent's or a preset's own ``models`` is yours to set, as above.
