# Runs

A **run** is one execution of a task inside the agent's sandbox: an agent's instructions, or an ad-hoc brief sent straight to `create_run`.

To attach files to the message that starts or feeds a run, pass a base64 ``files`` array (each ``{name, content_base64}``) to `create_run` or `send_message`. The agent finds them in its sandbox.

Lifecycle: ``READY`` → ``RUNNING`` → ``COMPLETED`` | ``FAILED`` | ``INTERRUPTED`` (paused mid-execution, resumes via ``WAITING``). ``CANCELED`` is the only fully terminal state. ``COMPLETED`` and ``FAILED`` runs carry on with a follow-up message (`send_message`), and `retry_run` runs one again where it rests with nothing new to say. To halt a run that's executing or waiting, call `stop_run`. It interrupts the run and, by default, deletes any pending scheduled messages so a later firing can't revive it (this is a pause to ``INTERRUPTED``, not the terminal ``CANCELED``). Wake a paused (``WAITING``/``INTERRUPTED``) run by sending it a message. `resume_run` is different: it replays a run from a chosen past tool call or an edited user message (debugging). To end a run for good, `cancel_run` moves it to ``CANCELED``: it is never dispatched again, its scheduled messages are deleted, and a channel contact's next message opens a fresh run. Cancel only when the run must end permanently. `get_run` reads a run cheaply: its ``state``, why it is not moving (``waiting_on``) or why its last turn stopped short (``stopped_by``), its ``result``, the fields an ``output_schema`` asked for in ``output``, and the files it attached, each read with `get_run_file`. `wait_for_run` blocks server-side until it settles and answers the same run. `list_messages` with its ``run_id`` reads the conversation. `get_run_trace` gives the full tool-by-tool view, with any oversized argument or result cut short behind a marker naming its full length. It pages: while ``has_more`` is true pass ``cursor`` back as ``cursor``, which also tails a growing run without refetching. Pass ``q`` to filter entries server-side (case-insensitive substring over tool, args, result, reasoning): recalling one action from a long conversation, your own included, is one filtered call, never a page-through.

## Starting, messaging and stopping

- **Start a run.** `create_run` from an ``agent_id`` or a ``preset_id``, briefed with ``text``. Pass ``integration_ids`` / ``asset_ids`` to attach a workspace integration or asset to the run itself, so a one-off reaches a connected account, database, mailbox or hosted site without an agent holding it (only backings your own key reaches), and ``config`` for run configuration this run alone takes. Pair it with `wait_for_run` when you need the result before continuing your own work, and skip the wait when the hand-off is your last step.
- **Give a running run one more account.** `add_run_integration` and `add_run_asset` link a workspace integration or asset to the run alone, from its next turn, as ``integration_ids`` / ``asset_ids`` do at start, and `remove_run_integration` / `remove_run_asset` take it away. `list_run_integrations` and `list_run_assets` list what the run holds beyond its agent's and preset's. A credential for one conversation is a vault item scoped to it with ``run_ids`` (see `operations.md`).
- **Send a message into an existing run.** `send_message` posts a message into a run and answers its ``message_id``. Without ``cron`` it dispatches the run immediately. With ``cron`` the message is parked and delivered when the expression resolves (**Parking a message on a schedule** below).
- **Ask a run's contact to connect something.** `create_connection` with ``type`` ``CONTACT`` and the run's ``run_id`` mints a link, valid for a day, that the run's contact opens with no account. Its ``ask`` names what: an integration (``kind: integration`` with ``types`` naming it, ``GMAIL``, or ``account`` to fix one the run already has), a managed resource the run's owner may use (``kind: asset`` with ``types``, ``TWILIO``, owned runs only), or a credential for that run (``kind: vault_item`` with ``name`` and ``type``), the same request `send_message` takes with ``action: provide``. The page shows the connection the link names and nothing else, the run itself sends the ``url`` through its channel with any words the contact needs, and once the contact acts the run is told as a platform message. `get_connection` reads where it stands. What the contact supplies serves that run alone, owned by the run's owner or by nobody. The run's ``allow_connections`` gates it like a card.
- **Answer what a run waits on.** A run parked on a card says so in ``waiting_on`` (``approval``, ``card``). The card is one of its messages (`list_messages` with its ``target_id``), and its ``card`` shows what it asks: an approval's ``tool_name`` and ``arguments``, a question's ``questions`` with the options to pick, the connection a card asks for. `answer_run` answers it, and once answered ``card.answer`` and ``card.answered_by`` say how and by whom.
- **Stop a run.** `stop_run` interrupts a run. Idempotent, so calling it on an already-stopped run is fine.
- **Replay or compress a run (debugging).** `resume_run` replays a run from a past tool call (``from_tool_call``) or an edited user message and answers the run that replays: a tool call replay runs in a new run unless ``debug_run_id`` names the run itself, which replays it in place. Waking a paused run is just `send_message`, not this. `abridge_run` compresses a long-lived run's history between turns. Both target *other* runs (a run cannot resume itself, and an executing run cannot be abridged), and both are VIBETASKING engine only: CLAUDE and CODEX runs reject them.

## Channel-attached agents

To talk to a channel's contact, open or continue their conversation with `start_conversation` on the channel, naming them in ``contact`` in the channel type's own form:

- **WhatsApp / SMS**: a phone number, with or without a leading ``+``. 7 to 15 digits.
- **Telegram**: a numeric chat_id. A ``@username`` does not work, because bots cannot start a chat with someone who has not first messaged them.
- **Instagram**: the contact's numeric IGSID (Instagram-scoped ID).
- **Messenger**: the contact's numeric PSID (page-scoped ID).
- **Slack**: a Slack conversation or user id (``C…``/``G…``/``D…``/``U…``).
- **Email**: a normal email address.
- **LinkedIn**: the contact's member id (``ACoAA…``). Profile URLs and ``in/slug`` handles are rejected.

Each channel is its own conversation, so the channel you pick decides how the contact is reached (a phone number fits both a WhatsApp and an SMS channel). A channel with no agent takes ``send: direct``, your team's message going out as is, and nothing runs. Starting a run of an agent with `create_run` never reaches a channel contact.

The ``text`` you pass is delivered to the channel's agent as a USER prompt. It is *not* the literal outbound payload, and it reaches the conversation marked as coming through your run. The agent reads it and decides what to send to the contact through the channel. Phrase it as an instruction to that agent (e.g. "Greet the contact and confirm their appointment for Tuesday at 3pm").

## Parking a message on a schedule

`create_run` and `send_message` both accept a 5-field ``cron`` expression: the message is parked and delivered when the schedule first resolves, then the schedule clears itself, so a parked message fires **once**. Use it for reminders, follow-ups, or a delayed hand-off, including on your own run. Recurring work belongs on an agent ``trigger`` instead, same convention. Pass ``timezone`` (an IANA name like ``Europe/Madrid``) to write the cron in the user's local wall-clock time: the platform stores the UTC form and keeps the zone so DST offset changes re-anchor the schedule, so reading it back shows the converted UTC expression, not the local one you wrote. When ``timezone`` is set, minute and hour must be single integers (``0 9 * * 1``, not ``*/15``). Scheduling takes the USER role only (the AGENT role cannot pass ``cron``), and a date-pinned cron whose moment has already passed is rejected rather than rolled to next year. `list_messages` with ``scheduled=true`` and the ``run_id`` lists the messages still waiting. `update_message` moves one to a new ``cron``, and `delete_message` cancels it before it fires. `stop_run` also drops every scheduled message on a run, but it pauses the run to do it. Runs park messages to themselves too, an ownerless run through its built-in ``send_message`` with no ``run_id`` (see **Self-scheduling** in `runtime.md`).

**Cron format.** 5-field standard cron: ``minute hour day-of-month month day-of-week``. Smallest granularity is one minute. The time shown in a run's context (e.g. ``14:30 (Europe/Madrid)``) is local, so prefer ``timezone`` over hand-converting. Omit it for cadences with no wall-clock anchor (every N minutes/hours) or when the user asked for UTC. For one-off future delivery, pick a cron that resolves to a single moment.

- Local 09:00 on weekdays, the user is in Madrid → ``"cron": "0 9 * * 1-5", "timezone": "Europe/Madrid"``.
- Every weekend at 9pm, but we want it in Australia → ``"cron": "0 21 * * 0,6", "timezone": "Australia/Sydney"``.
- Every 15 minutes (cadence, no anchor) → ``"cron": "*/15 * * * *"``, no ``timezone``.
