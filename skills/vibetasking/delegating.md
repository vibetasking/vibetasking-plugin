# Calling a toolkit tool directly vs. delegating

Once `list_toolkit_tools` has shown you a tool, you have two ways to make it run. Choose deliberately. Over the MCP the direct way is a headless call. From a run it is the toolkit's own command in your sandbox, when something this run is linked to backs it. Everything else goes to a run you start.

**Know the tool's parameters before you call it, every time.** Tool names likewise come from the listing, never from guesswork: a guessed name or parameter burns a failed round trip for each try. The listing carries each tool's `parameters` JSON schema whenever the catalog fits its size budget, and its `schemas` field tells you which case you're in. When `schemas` says omitted, call `get_toolkit_tool` (the toolkit as ``name``, the tool as ``tool``) for each tool you intend to run and read the schema there. A tool's name and one-line summary do not describe its arguments: a send tool that takes both a plain-text and a rich-text form documents that only in the schema, and calling it on the summary alone is how formatting reaches a recipient as raw markup. The listing also reads a toolkit nothing has connected yet: it is how you tell a user what a toolkit covers, or check that a delegation target carries what the task needs, with nothing linked and nothing running. For a toolkit a run is linked to, the command's own ``--help`` in that sandbox is the contract.

- **Call it directly**, over the MCP, with `call_toolkit_tool` when the tool belongs to a **directly-callable** toolkit and you just need its result. Directly-callable covers: every Composio and Pipedream integration, every OpenAPI integration, every **MCP** integration over an HTTP/SSE transport (a stdio one runs a command and must be delegated via a run), the **Twilio**, **Email** and **Stripe** assets, and every **channel** (WhatsApp, Telegram, Instagram, Messenger, Slack, LinkedIn and custom channels, plus SMS/Email). This is headless: no agent, no run, fast. A tool the workspace gates behind human approval is refused until a person has explicitly agreed to that action: ask the person you are working for, then call again with ``human_approved`` set to true, and never set it on their behalf. Pass the toolkit as ``name`` (the identifier `list_toolkit_tools` took), identify the connected instance with exactly one of ``integration_id`` / ``asset_id`` / ``channel_id``, name the ``tool`` exactly as returned by `list_toolkit_tools` (names carry the toolkit prefix, ``holded_list_all_taxes``, where the toolkit's CLI help and a template's prompt use the bare ``list_all_taxes``), pass ``args``, and optionally stage ``input_files`` into its sandbox (this is how you attach a file to any send head-less: stage it under a ``filename``, then pass that exact name in the tool's file-path param. The tool's schema names that param and declares it as a sandbox-relative path string or array, e.g. Gmail's ``files``). It answers the tool's ``result`` and its ``files``. Any files the tool produces come back as short-lived signed URLs in ``files`` (never inlined), so fetch their bytes yourself. **Pass an explicit recipient on channel sends**, since there's no run to supply a bound contact.
- **Run it yourself**, from a run, when the toolkit is backed by an integration, asset or channel linked to this run: it is a command in your sandbox, and the rest of your instructions carry how to call one. A run holds no headless call of its own, so a toolkit nothing links to this run reaches you through a run you start with that backing attached (see **A one-off that needs a workspace backing** below).

  **Operating an asset splits by type.** A **SUPABASE** asset is reached through `read_asset_api` and `call_asset_api` (see **Reaching an asset's own database** in `data.md`) because it's a database, not an action set. Over the MCP, a **TWILIO** or **EMAIL** asset is operated through `call_toolkit_tool` with its ``asset_id``, and a **STRIPE** asset answers the dedicated Stripe operations (`list_stripe_products`, `create_stripe_product`, `create_stripe_onboarding_link` and their siblings) for onboarding, catalog and payments plus `call_toolkit_tool` for what they leave out, a checkout session among them. From a run, a TWILIO, EMAIL or STRIPE asset linked to it is a command of its own in the sandbox, and a STRIPE asset also answers the dedicated Stripe operations. A **SITE** asset (a hosted website) has dedicated operations: `deploy_site` publishes a zip of built static output as the new production version, fetched from an https ``source_url`` or, for a bundle you hold, presigned with `create_site_upload_url`, PUT there, then passed as that ``staged_path`` (from a run, `deploy_site` takes the sandbox ``directory`` of the built output and does all three), `list_site_deployments` lists the deployment history plus the currently-served ``canonical_deployment``, `rollback_site_deployment` re-points production at a previous deployment, `get_site_bundle_url` returns a short-lived download URL for the exact bundle a deployment shipped (any deployment from the listing: every deploy retains its bundle, so edits start from the real source, not from scraping the live site), and `list_site_secrets`/`set_site_secrets`/`delete_site_secret` manage the secrets its server functions read (values are write-only and live at once). A **PROXY** asset (dedicated proxy IPs with their own credential and a rotating endpoint) is read through `list_asset_proxies` (endpoint list, credential, current-cycle usage) and re-shaped through `resize_asset_proxies` (same quote flow as provisioning: `quote_asset` with the new ``countries``/``bandwidth_gb`` and the asset's ``asset_id``, then pass that ``quote``). Linked to an agent, it routes that agent's runs' outbound traffic (browser, shell and toolkit HTTP) through the allocation. Reading them needs ``assets:read`` and resizing ``action:provision_assets``, as provisioning does. The site writes (`deploy_site` and its siblings) need ``action:proxy_assets``. A site's source lives on its own disk, mounted at `sites/<reference>/` in every run the site reaches, and a run rebuilds from it. Changing a site never requires a run when you can edit files: start from the served bundle (`get_site_bundle_url`), apply the edits, zip the result, and ship it with `deploy_site`, and a run that next deploys from the source is refused until it fetched that bundle and carried your edits into the source. Every bundle you deploy carries a favicon, because the platform wears the site's declared icon on its resource card and a site without one shows a generic globe: write a ``favicon.svg`` at the bundle root holding one emoji that suits the app, `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 100 100"><text y=".9em" font-size="90">🚀</text></svg>`, and declare it in the ``index.html`` head with `<link rel="icon" type="image/svg+xml" href="/favicon.svg">`. A delegated run starts cold and re-reads the bundle to learn what you already know, so delegate site work only as a last resort.

- **Delegate via a run** when the work needs the full agentic stack. A platform run is a capable generalist out of the box: it browses the web and operates sites, runs shell and Python, produces documents and spreadsheets, and dispatches its own sub-agents. Over the MCP, never conclude a capability is missing without delegating first: delegation is also the route for operating a browser, multi-step or branching tasks beyond what your own tools can carry, a client for a connection secret (``psql``, ``mysql``, ``mongosh``, ``redis-cli``, ``curl``, ``amqp-get``, ``mosquitto_sub``, ``ldapsearch``, ``ssh``, ``sftp``, which need a sandbox and the run's exported connection), or anything `call_toolkit_tool` rejects with **422** ("isn't directly callable"). Those toolkits are run-gated: they only work inside the agent's sandbox with a live run lifecycle, so hand the work to an internal run instead of trying to call the tool directly. From a run, a run you start is the same kind of generalist you are, with the same sandbox: what it adds is a clean context, another agent's prompt, and the backings you attach when you start it, so delegation is the route for a toolkit whose integration, asset or channel is not linked to this run, work an existing agent's prompt already frames, and long or branching work you would rather keep out of this conversation. Work your own sandbox already does costs the user a second run when you delegate it, and that run starts cold. To delegate:
  1. Point `create_run` at a **preset, or an agent, that already carries the required toolkit** (see **Choosing the delegation target** below). Pass realistic ``text``.
  2. `wait_for_run(run_id)` to block server-side (≤50s long-poll) until it settles on ``COMPLETED`` / ``FAILED`` / etc., or read `get_run` for a cheap non-blocking check (its ``state``, and ``waiting_on`` when it is not moving). A run that stays ``PENDING`` across waits is queued behind the workspace's concurrency cap, not broken: its settled result is forwarded to your run as a message when it finishes, so tell the user it's queued and settle your turn rather than promising an imminent number you can't produce yet. (The forward-back is the default for any run you start except channel-attached ones, whose conversation settles after every exchange. Start those with ``watch: true`` or call `watch_run` to opt in, or read `get_run` instead. Pass ``watch: false`` to `create_run` for a fire-and-forget run that never notifies you. `unwatch_run` stops the notices from a run you watch.)
  3. Read the outcome from the settled run's ``result``, then `get_run_trace(run_id)` for the tool-by-tool view of what it actually did (every call, args, result, reasoning). The settled run names its deliverables in ``attachments``, and `get_run_file` with each name answers a link to its bytes for the next hour. Over the MCP, fetch the bytes from the link directly. The run's own disk is the one `get_run` lists at the root of its ``mounts``: `list_files` with its ``disk_id`` lists paths you don't already have, `get_file` answers a link to one, and `create_file_archive` fetches the run's whole output (or one folder of it) as a single zip. From a run, `get_file` with an ``output_path`` lands one in your sandbox, `list_files` lists paths you don't already have, and `create_file_archive` answers one link to a zip of the run's whole output (or one folder of it) to fetch with ``curl`` and unzip. Never instruct a run to relay file content through its messages (base64 or otherwise), since files travel by path or URL. When the user marks a stored agent or preset file off-limits (a shared engine script, a config only they maintain), make it real with `create_disk_rule` of ``type`` ``LOCKED`` on its disk: no run writes past it, and `list_disk_rules` shows the locks.

  **A delegated run can delegate in turn.** It keeps the ``vibetasking`` toolkit and can start runs of its own, which is how chained executions are built. The prompt names the next agent (or the agent itself) as a mention and instructs the dispatch (see **Routing agents** in `building.md`).

## Choosing the delegation target

You pick the target yourself, reusing an existing one or building one. An agent's engine is the ``engine`` of the first entry of its ``turn`` that can run: its own ``config.models.turn`` when set, else its preset's, else the workspace's, else the platform's. A CLAUDE agent is as good a target as a VIBETASKING one. An agent whose ``turn`` puts **CODEX** first is a target a user chose deliberately, never the one you reach for to get a task done. `get_purposes` with its ``agent_id`` answers its ``turn`` as it runs. A run started from a preset, or with no agent at all, takes its ``turn`` from that preset the same way, unless its own ``config.models`` names one. In order of preference:

- **Reuse an existing agent** whose links already include the toolkit you need (`list_agents`, then `list_agent_integrations` and `list_agent_assets` on a candidate, and its ``turn``), and `create_run(agent_id=...)`. This is best: the agent's prompt already frames the task. If `create_run` rejects it as **archived**, archiving was a user decision: pick another target or ask, and don't quietly restore it with `update_agent` to unblock your call. The same restraint applies to any workspace configuration (enabled flags, channels, triggers): mutate it because the user asked for that change, never as a workaround.
- **Start a bare run**, `create_run(text=...)` with no preset or agent at all, when you only need a generic capable runner. The run lands in your key's workspace on the workspace's default preset (its ``turn``, else the workspace's, else the platform's), or, when the workspace sets none, on the platform default, which is what the ``Ultra`` tier carries, with the standard toolkits (browser, shell, sub-agents included). Describe the whole task in ``text``. Pass ``config`` (the run-configuration object, **Run configuration** in `configuration.md`) to shape the run itself: ``models``, ``output_schema``, and the rest, overriding any agent or preset value for this run only. A bare run lands on that default, so leave ``config.models`` unset unless the user asked for a different tier or named a model. The model you run on yourself plays no part in that choice, and the name your own runtime gives it is not a platform identifier. This is the default shape for a one-off: nothing to discover, create, or clean up.
- **Start against a platform preset** (`create_run(preset_id=...)` with one of the platform's presets, the ones `list_presets` answers with a null ``workspace_id``) when the user asked for a tier other than the one a bare run lands on (see **Choosing a tier** in `configuration.md`). The run likewise lands in your key's workspace, on the preset's own ``turn`` (the workspace's or the platform's when it names none). The platform's presets are general-purpose and won't carry workspace-specific integrations.

**A one-off that needs a workspace backing still takes one of the shapes above.** Pass ``integration_ids`` / ``asset_ids`` to `create_run` and the connected account, database, mailbox, phone number, or hosted site is attached to that run itself, so a bare run or a platform-preset run reaches it with no agent in between. The run's toolkit resolves the backing exactly as an agent-linked one would. Two limits: they apply to a run you create, not to one you retry or message, and you can only pass backings your key may read, which is the ones you created, the workspace's public ones and any shared with you (all of the workspace's for an admin), so check that before you promise one. **So don't create an agent as a delegation vehicle.** An agent is for work the user will run again, and a one-off leaves nothing behind.
