# Calling a toolkit tool directly vs. delegating

Once `list_toolkit_tools` has shown you a tool, you have two ways to make it run. Choose deliberately. Over the MCP the direct way is a headless call. From a run it is the toolkit's own command in your sandbox, when something this run is linked to backs it. Everything else goes to a run you start.

**Know the tool's parameters before you call it, every time.** Tool names likewise come from the listing, never from guesswork: a guessed name or parameter burns a failed round trip for each try. The listing carries each tool's `parameters` JSON schema whenever the catalog fits its size budget, and its `schemas` field tells you which case you're in. When `schemas` says omitted, call `get_toolkit_tool` (the toolkit as ``name``, the tool as ``tool``) for each tool you intend to run and read the schema there. A tool's name and one-line summary do not describe its arguments: a send tool that takes both a plain-text and a rich-text form documents that only in the schema, and calling it on the summary alone is how formatting reaches a recipient as raw markup. The listing also reads a toolkit nothing has connected yet: it is how you tell a user what a toolkit covers, or check that a delegation target carries what the task needs, with nothing linked and nothing running. For a toolkit a run is linked to, the command's own ``--help`` in that sandbox is the contract.

- **Call it directly**, over the MCP, with `call_toolkit_tool` when the tool belongs to a **directly-callable** toolkit and you just need its result. Directly-callable covers: every Composio and Pipedream integration, every OpenAPI integration, every **MCP** integration over an HTTP/SSE transport (a stdio one runs a command and must be delegated via a run), the **Twilio**, **Email** and **Stripe** assets, and every **channel** (WhatsApp, Telegram, Instagram, Messenger, Slack, LinkedIn and custom channels, plus SMS/Email). This is headless: no agent, no run, fast. A tool the workspace gates behind human approval is refused until a person has explicitly agreed to that action: ask the person you are working for, then call again with ``human_approved`` set to true, and never set it on their behalf. Pass the toolkit as ``name`` (the identifier `list_toolkit_tools` took), identify the connected instance with exactly one of ``integration_id`` / ``asset_id`` / ``channel_id``, name the ``tool`` exactly as returned by `list_toolkit_tools` (names carry the toolkit prefix, ``holded_list_all_taxes``, where the toolkit's CLI help and a template's prompt use the bare ``list_all_taxes``), pass ``args``, and optionally stage ``input_files`` into its sandbox (this is how you attach a file to any send head-less: stage it under a ``filename``, then pass that exact name in the tool's file-path param. The tool's schema names that param and declares it as a sandbox-relative path string or array, e.g. Gmail's ``files``). It returns ``{result, files}``. Any files the tool produces come back as short-lived signed URLs in ``files`` (never inlined), so fetch their bytes yourself. **Pass an explicit recipient on channel sends**, since there's no run to supply a bound contact, except under a turn key, where the run does (see **Inside a turn** in `external.md`).
- **Run it yourself**, from a run, when the toolkit is backed by an integration, asset or channel linked to this run: it is a command in your sandbox, and the rest of your instructions carry how to call one. A run holds no headless call of its own, so a toolkit nothing links to this run reaches you through a run you start with that backing attached (see **A one-off that needs a workspace backing** below).

  **Operating an asset splits by type.** A **SUPABASE** asset is reached through `asset_proxy_read` and `asset_proxy_call` (see **Reaching an asset's own database** in `data.md`) because it's a database, not an action set. Over the MCP, a **TWILIO** or **EMAIL** asset is operated through `call_toolkit_tool` with its ``asset_id``, and a **STRIPE** asset answers the dedicated Stripe endpoints (`get_stripe_catalog`, `create_stripe_product`, `stripe_onboarding_link` and their siblings) for onboarding, catalog and payments plus `call_toolkit_tool` for what they leave out, a checkout session among them. From a run, a TWILIO, EMAIL or STRIPE asset linked to it is a command of its own in the sandbox, and a STRIPE asset also answers the dedicated Stripe endpoints. A **SITE** asset (a hosted website on Cloudflare Pages) has dedicated endpoints: `site_deploy` uploads a zip of built static output as the new production version (multipart ``file``, JSON ``content_base64``, or for a large bundle presign with `site_deploy_url`, PUT the zip there, then pass that ``staged_path``), `site_deployments` lists the deployment history plus the currently-served ``canonical_deployment_id``, `site_deployment_rollback` re-points production at a previous deployment, `site_bundle` returns a short-lived download URL for the exact bundle a deployment shipped (the served deployment by default, or any ``deployment_id`` from the listing: every deploy retains its bundle, so edits start from the real source, not from scraping the live site), and `site_secrets`/`site_secrets_put`/`site_secret_delete` manage the secrets its Pages Functions read (values are write-only and apply from the next deployment). A **PROXY** asset (dedicated proxy IPs with their own credential and a rotating endpoint) is read through `asset_proxies` (endpoint list, credential, current-cycle usage) and re-shaped through `asset_proxies_resize` (same quote flow as provisioning: `quote_asset` with the new ``countries``/``bandwidth_gb``, then pass the ``quote_id`` as ``accept_quote``). Linked to an agent, it routes that agent's runs' outbound traffic (browser, shell and toolkit HTTP) through the allocation. Reading them needs ``assets:read`` and resizing ``action:provision_assets``, as provisioning does. The site writes below (`site_deploy` and its siblings) need ``action:proxy_assets``. Changing a site never requires a run when you can edit files: start from the served bundle (`site_bundle`), apply the edits, zip the result, and ship it with `site_deploy`. Every bundle you deploy carries a favicon, because the platform wears the site's declared icon on its resource card and a site without one shows a generic globe: write a ``favicon.svg`` at the bundle root holding one emoji that suits the app, `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 100 100"><text y=".9em" font-size="90">🚀</text></svg>`, and declare it in the ``index.html`` head with `<link rel="icon" type="image/svg+xml" href="/favicon.svg">`. A delegated run starts cold and re-reads the bundle to learn what you already know, so delegate site work only as a last resort.

- **Delegate via a run** when the work needs the full agentic stack. A platform run is a capable generalist out of the box: it browses the web and operates sites, runs shell and Python, generates images and video, produces documents and spreadsheets, and dispatches its own sub-agents. Over the MCP, never conclude a capability is missing without delegating first: delegation is also the route for operating a browser, multi-step or branching tasks beyond what your own tools can carry, a client for a connection secret (``psql``, ``mysql``, ``mongosh``, ``redis-cli``, ``curl``, ``amqp-get``, ``mosquitto_sub``, ``ldapsearch``, which need a sandbox and the run's exported connection), or anything `call_toolkit_tool` rejects with **422** ("isn't directly callable"). Those toolkits are run-gated: they only work inside the agent's sandbox with a live run lifecycle, so hand the work to an internal run instead of trying to call the tool directly. From a run, a run you start is the same kind of generalist you are, with the same sandbox: what it adds is a clean context, another agent's prompt, and the backings you attach when you start it, so delegation is the route for a toolkit whose integration, asset or channel is not linked to this run, work an existing agent's prompt already frames, and long or branching work you would rather keep out of this conversation. Work your own sandbox already does costs the user a second run when you delegate it, and that run starts cold. To delegate:
  1. Point `start_run` at a **preset, or an agent on any engine but EXTERNAL, that already carries the required toolkit** (see **Choosing the delegation target** below). Pass realistic ``text``.
  2. `wait_for_run(run_id)` to block server-side (≤50s long-poll) until it settles on ``COMPLETED`` / ``FAILED`` / etc., or poll `get_run_status` for a cheap non-blocking check (``done`` is true once it rests). A run that stays ``PENDING`` across waits is queued behind the workspace's concurrency cap, not broken: its settled result is forwarded to your run as a message when it finishes, so tell the user it's queued and settle your turn rather than promising an imminent number you can't produce yet. (The forward-back is the default for any run you start except channel-attached ones, whose conversation settles after every exchange. Start those with ``watch: true`` or call `watch_run` to opt in, or poll `get_run_status` instead. Pass ``watch: false`` to `start_run` for a fire-and-forget run that never notifies you. `unwatch_run` stops the notices from a run you watch.)
  3. Read the outcome from the settled status/result, then `get_run_trace(run_id)` for the tool-by-tool view of what it actually did (every call, args, result, reasoning). The settled status lists the run's deliverables in ``files`` as signed download URLs. Over the MCP, fetch the bytes from the URL directly: `get_download_url` covers paths outside ``result.attachments``, `list_files_in_entity` paths you don't already have, and `get_archive_url` fetches a run's whole output (or one directory of it) as a single zip. From a run, `download_file_from_entity` with the run as the entity and the file's ``path`` lands one in your sandbox (``output_path`` picks where), `list_files_in_entity` lists paths you don't already have, and `get_archive_url` returns one signed URL for a zip of the run's whole output (or one directory of it) to fetch with ``curl`` and unzip. Never instruct a run to relay file content through its messages (base64 or otherwise), since files travel by path or URL. When the user marks a stored agent or preset file off-limits (a shared engine script, a config only they maintain), make it real with `protect_file_in_entity` (or ``protected: true`` on the upload): the file materialises read-only for agents in every sandbox and agent writes to it are refused, while `list_files_in_entity` shows the protected set.

  **A delegated EXTERNAL run is a leaf.** A run on the EXTERNAL engine that was itself started by another run cannot start further runs (the attempt is rejected with 409), since its turns are worked by an agent outside the platform. Every other engine carries no such cap: a delegated VIBETASKING run keeps the ``vibetasking`` toolkit and can start runs of its own, which is how chained executions are built. The prompt names the next agent (or the agent itself) as a mention and instructs the dispatch (see **Routing agents** in `building.md`).

## Choosing the delegation target

You pick the target yourself, reusing an existing one or building one. The one hard rule: **never delegate to an EXTERNAL agent.** An agent on the **EXTERNAL** engine does no work of its own: every turn it takes is offered to an agent outside the platform, and it waits until that agent claims it. **CLAUDE** is the platform default, the engine of every agent and run whose chain names none, so it is as good a target as VIBETASKING. An agent on **CODEX** is a target a user chose deliberately, never the one you reach for to get a task done. An agent's engine is its own ``engine`` when set, else the ``engine`` of the preset it reads (its ``preset_id``, else the workspace's default preset), else CLAUDE: ``agents.engine`` and ``presets.engine`` are both nullable, and null means inherit, so read both before you pick an agent. A run started from a preset, or with no agent at all, takes its engine from that preset the same way, unless the start names another. In order of preference:

- **Reuse an existing agent** whose enabled toolkits already include the toolkit you need (`find_providers` / `query_data` on ``agents`` to locate one, then read its ``engine``), and `start_run(agent_id=...)`. This is best: the agent's prompt already frames the task. If `start_run` rejects it as **archived**, archiving was a user decision: pick another target or ask, and don't quietly un-archive it via `update_data` to unblock your call. The same restraint applies to any workspace configuration (enabled flags, channels, triggers): mutate it because the user asked for that change, never as a workaround.
- **Start a bare run**, `start_run(text=...)` with no preset or agent at all, when you only need a generic capable runner. The run lands in your key's workspace on the workspace's default preset (its engine, CLAUDE when it names none, and its model), or, when the workspace sets none, on the platform default, which is what the ``Ultra`` tier carries, with the standard toolkits (browser, shell, sub-agents included). Describe the whole task in ``text``. Pass ``data`` (the run-configuration object, **Run configuration** in `configuration.md`) to shape the run itself: ``model``, ``reasoning_effort``, ``output_schema``, and the rest, overriding any agent or preset value for this run only. A bare run lands on that default, so leave ``data.model`` and ``data.reasoning_effort`` unset unless the user asked for a different tier or named a model. The model you run on yourself plays no part in that choice, and the name your own runtime gives it is not a platform identifier. This is the default shape for a one-off: nothing to discover, create, or clean up.
- **Start against a system preset** (`start_run(preset_id=...)` with a system preset from `query_data` on ``presets`` where ``workspace_id is null``) when the user asked for a tier other than the one a bare run lands on (see **Choosing a tier** in `configuration.md`). The run likewise lands in your key's workspace, on the preset's own engine (CLAUDE when it names none). System presets are general-purpose and won't carry workspace-specific integrations.

**A one-off that needs a workspace backing still takes one of the shapes above.** Pass ``integration_ids`` / ``asset_ids`` to `start_run` and the connected account, database, mailbox, phone number, or hosted site is attached to that run itself, so a bare run or a system-preset run reaches it with no agent in between. The run's toolkit resolves the backing exactly as an agent-linked one would. Two limits: they apply to a run you create, not to a ``run_id`` re-dispatch, and you can only pass backings your key may read, which is the ones you created, the workspace's public ones and any shared with you (all of the workspace's for an admin), so check that before you promise one. **So don't create an agent as a delegation vehicle.** An agent is for work the user will run again, and a one-off leaves nothing behind.
