## How the agent executes inside a run

A VIBETASKING run drops the agent into a **sandbox** (a Linux filesystem) with a small core toolset and a catalog of toolkits invoked through shell commands. Everything below is what the agent already knows and does on its own. You need it for two reasons: to read a run trace and understand what you're seeing, and to write agent prompts in the runtime's own terms (see **Writing agent prompts** in `building.md`).

- **Who owns a run.** Read this before the rest of the section: ownership decides part of the toolset. A run started by a person in the app, or by an API key like yours, **acts as a profile**: ``runs.profile_id`` holds it, and that person is the run's user. A run bound to a channel contact has no owning profile (``runs.profile_id`` is null) and is called **ownerless**: its counterpart is an external contact, not a platform user. That covers every run of a channel agent, whoever starts it: the conversation run an incoming message opens, a `start_run` with ``contact_id`` (it joins that contact's conversation), and a scheduled fire, which takes the contact stored on its trigger. The one exception is a contact who is a member of the workspace: on WhatsApp, SMS, voice and email, a contact whose phone or email is exactly one member's makes that member the run's owning profile, so their own conversation runs as them. The runs such a conversation starts with ``start_run`` stay ownerless too. A run of an agent with no channel, scheduled or webhook fired included, runs as the agent's profile (or the firing asset's). ``start_run`` (**Platform orchestration**) exists **only** on ownerless runs, because on an owned run the owner is already the human in the loop, and ``dispatch_human`` (**Talking to people**) exists only on interactive runs bound to a channel contact. Don't probe for either by starting a run and asking it to list its tools: a run you start here without a contact is profile-owned and bound to no channel, so it reports both missing, and that says nothing about the channel's conversation runs. When a question genuinely needs a live run to settle, remember a diagnostic run is a real run in the user's workspace, billing credits and appearing in their run list (and in the channel's conversation view when bound to a contact). Archive it once answered (`update_data` setting ``archived_at`` on its ``runs`` row) so the user never finds a stray conversation they cannot place.
- **Sandbox layout.** The agent's instructions and its distilled recipe are rendered into its system prompt, and every stored artifact materializes at ``agent/<name>``. User uploads, message attachments, and the run's own deliverables live at the sandbox root. All paths are relative. Files the agent writes under ``agent/`` persist as artifacts for future runs.
- **Core tools.** ``shell_exec`` (any Linux command, with Python 3 plus pandas, openpyxl, plotly and scipy preinstalled), ``file_read`` / ``file_write`` / ``edit_file``, ``message_user`` (interactive runs only), ``dispatch_agent`` (sub-agents, below), ``dispatch_human`` (operator handoff, on interactive runs bound to a channel contact only), and ``final_result``, the terminal call that delivers the outcome as ``text`` plus ``attachments``, plus any custom fields the run's ``output_schema`` declares.
- **Toolkits are CLIs** reached through ``shell_exec``: platform toolkits as ``<toolkit> <action> --json '{...}'``, Composio as ``composio <toolkit> <action>``, Pipedream as ``pipedream <toolkit> <action>``. A database, cache, mail server, mailbox, broker or directory the run holds as a secret is reached with the vendor's own client (``psql``, ``mysql``, ``mongosh``, ``redis-cli``, ``curl``, ``amqp-get``, ``mosquitto_sub``, ``ldapsearch``) through the environment variables the platform exports for it (see **Secrets and credentials** in `operations.md`). The agent discovers an action's parameters with ``<toolkit> <action> --help``. When more than one backing of a type is connected, it picks one with ``--account <id>``, the id a mention of the integration/asset/channel carries. A large JSON body travels best by file: the agent writes it in the sandbox and passes ``--json-file body.json`` instead of inlining it, so the payload never rides through shell quoting. The agent isn't making HTTP calls directly, it's running shell commands that wrap them, and it prefers existing toolkits over raw ``curl``.
- **Sub-agents.** ``dispatch_agent`` hands a bounded subtask to a sub-agent that shares the sandbox and most tools but not the chat history. The agent fans independent dispatches out in parallel. File arguments arrive resolved: a ``message`` or ``output_schema`` given as a sandbox file path is delivered as that file's content, loaded into the sub-agent's context before it starts, so the path form is the standard way to reuse a large prompt or schema across many dispatches. A run trace records the raw arguments only, so a dispatch whose ``message`` is a short file path still delivered the full content to the sub-agent. A specialist runs on the model and reasoning effort this deployment pins to it rather than the agent's own, so a trace shows a dispatch billing a model the agent never carried. Three specialists are standard practice:
  - ``specialist="extractor"``: the canonical way to pull structured data out of a large or unstructured file: the file goes in ``path`` and is likewise loaded into the extractor's context up front, a JSON schema in ``output_schema`` (required, the result comes back in that exact shape), an optional ``message`` says what to extract. One dispatch per file, and for many files, parallel dispatches sharing one schema file. ``save_as`` writes the result to a sandbox file instead of returning it inline.
  - ``specialist="browser"``: the canonical way to browse, the sub-agent operates the run's shared browser session.
  - ``specialist="viewer"``: the canonical way to work with a recording in the sandbox: the file goes in ``path`` and is loaded into the viewer's context up front, an optional ``message`` asks what to look for. It watches the video or listens to the audio itself and answers with timestamps, which is how a run reads a recording the agent's own model cannot.
  On an agent whose ``engine`` is ``CLAUDE`` or ``CODEX``, delegation is the CLI's own sub-agent: ``dispatch_agent`` serves ``extractor`` and ``viewer`` only, the agent drives the browser itself through the ``browser`` toolkit, and web search is the CLI's own tool rather than the ``web_search`` toolkit. On those engines the core tools are the CLI's own as well (its shell, file reading and editing tools), the platform's tools are shell commands (``humane message_user``, ``humane dispatch_human``, ``agent dispatch_agent``), and there is no ``final_result``: the reply the turn ends with and the files left at the sandbox root are the outcome. A trace of such a run shows those names, and a prompt that says ``final_result`` still reads correctly there.
- **The browser is a last resort.** For plain lookups the agent uses the ``web_search`` toolkit, for fetching a URL ``curl``/``wget``, and the browser only when real navigation is required or the prompt demands it. To rule it out entirely, set ``browser: false`` in ``data`` (agent, preset, or run): the run then carries no browser toolkit, the agent is never told about browsing, and the ``browser`` sub-agent specialist is rejected. Use it for agents that must never navigate the web.
- **Local browser mode.** With ``browser_local: true`` in ``data`` (agent, preset, or run, cascading like other settings), the run's browser drives the **user's own Chrome** through the VibeTasking Chrome extension instead of the sandbox browser, reusing their cookies, sessions, and fingerprint. Use it for sites behind login walls or anti-bot measures. The run publishes a pairing token in ``run.feed`` (``local-browser:<token>``), and the app auto-connects an installed extension, and if none attaches within a short grace, browser commands fail until it connects or the agent switches to the sandbox browser with its ``browser_mode`` tool. Delegated sub-runs inherit the setting.
- **Talking to people.** ``message_user`` (progress, and questions, with ``action`` ``question`` and its multiple-choice options preferred) and ``final_result`` reach the **platform side only**: the app user, or the run that delegated this one. On an interactive run ``message_user`` can also hand the live browser to the user (``action`` ``browser``) for a captcha, a 2FA approval or a login checkpoint, and the run resumes once they've acted, so a verification wall pauses the run rather than failing it. On a channel-attached run the external contact is reached exclusively through the channel toolkit (``whatsapp send_message``, ``telegram …``), and the run is expected to have replied to the contact before finishing. Non-interactive runs have no ``message_user`` at all, so they cannot pause to ask anything. On a run bound to a channel contact (above) the same interactive gate also carries ``dispatch_human``, the agent's way of putting a person on the conversation: it halts the run, switches the conversation to operator mode, notifies the workspace, and routes further contact messages to that operator instead of the agent until they hand it back. It answers both "the contact asked for a real person" and "stop attending this contact from now on", and it works on every channel type. ``dispatch_human`` sends the contact nothing itself. By default the runtime nudges the agent once to warn the contact through the channel toolkit before handing off, so the contact is not left hanging. On a persona account that warning breaks the persona, so when the agent must never reveal an AI or a team behind the account, write it explicitly in the prompt (for example "never announce the handoff") and the agent hands off without a word, at the cost of the nudge turn on every handoff. When the prompt settles the question for every handoff, also set ``allow_unannounced_handoff: true`` in ``data`` (agent, preset, or run, cascading like other settings): ``dispatch_human`` then skips the nudge and hands off silently on the first call, with no other change to its behavior. To take outbound messaging away from the agent entirely, set ``silent: true`` in ``data``: channel sends are refused at the tool level, the agent keeps receiving the contact's messages and doing its internal work, and ``dispatch_human`` proceeds with no nudge. Use it for conversations a person handles personally while the agent only records. To make that the handoff's own behavior, set ``silent_handoff`` in the channel's config (see **Conventions** in `operations.md`): ``dispatch_human`` then notifies the workspace and flips the conversation silent instead of switching it to operator mode, so every reply a person takes over keeps its agent as a silent bookkeeper.
- **Secrets by name.** The agent uses stored secrets as ``$NAME`` in any shell command or tool argument. A closed secret (a login, a key, a card) rides the sandbox as a decoy the platform swaps for the real value only on its way out, to its site or API, so the value never enters the transcript, while a readable one (an identity, a variable) is held as itself. A TOTP field yields a fresh 2FA code on every use. A credential a tool echoes back in its error output (a key or token inside a URL or a header) is masked before it reaches you, and one that slips through is never yours to reuse: reason from the status code and message, never lift the value into another call.
- **Step tracking.** With ``planning`` on (the default), the agent maintains a ``todo.md`` checklist in the sandbox for multi-step work, one checkbox per item, updated as it goes.
- **Skills** are read-only guidance files under ``system/skills/`` the agent reads before first using a toolkit. You don't manage them, but a trace showing a ``file_read`` of a SKILL.md is the agent doing this. Over the MCP, the ones usable through the API are yours to read too: `list_skills` indexes them, `get_skill` returns one's guidance (ending in a manifest of its companion files), and `get_skill_file` fetches a companion script or reference document. To run a fetched script yourself, save it under the ``system/skills/...`` path the guidance cites, since its documented invocations assume that layout. From a run, your own sandbox carries the same files under ``system/skills/``, so read a skill there before wiring what it covers.
- **Platform orchestration.** A profile-owned run carries the ``vibetasking`` toolkit, the same public API surface you are using now (``start_run``, ``send_message``, ``query_data``, ``upsert_agent``, …), invoked as a CLI and acting as the owning profile. An ownerless run (**Who owns a run**, above) instead has the built-in ``start_run`` tool (alongside ``message_run``, ``get_run_status``, ``watch_run``, ``unwatch_run`` and ``stop_run`` for following what it started), which starts another agent's run and is authorised only when the target's UUID appears literally in the calling prompt, and a mention of the target provides exactly that. Either way, chaining agents is a prompt concern: write the target as a mention and instruct the dispatch (see **Routing agents** in `building.md`).
- **Self-scheduling.** Every run can park a message to its future self with a 5-field ``cron`` and an optional IANA ``timezone``: the message is parked, fires once when the schedule first resolves, and arrives as if just sent (**Parking a message on a schedule** in `runs.md` carries the full contract). A profile-owned run does it through the CLI: ``vibetasking send_message`` on its own run id with ``cron``. An ownerless run carries built-ins instead: ``schedule_message(text, cron, timezone, attachments)`` parks one, ``list_scheduled_messages()`` lists the pending ones, and ``cancel_scheduled_message(message_id)`` drops one. This list is authoritative: write timed follow-ups straight into an agent prompt (a catch-up when the contact has not replied in two days) instead of probing a live agent to discover whether the tools exist. Parked rows are ordinary ``messages`` rows with ``cron`` set, so from here `query_data` shows any run's pending follow-ups. Two habits keep wake-ups honest. **Reschedule, never stack**: pending wake-ups appear in each turn's ``<scheduled>`` block, so when one already covers what you are about to park, rewrite its ``cron`` instead of adding a second. **A repeat check states its exit**: re-parking because the awaited thing is unresolved is fine so long as the text says what ends the loop, and the wake is dropped once it does. A repeat with a real cadence is an agent with a trigger, not a chain of wake-ups.
