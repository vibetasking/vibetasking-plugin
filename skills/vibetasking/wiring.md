## Integrations, assets, channels

- **Integrations** are OAuth connections to third-party services via Composio or Pipedream (the row's ``provider``). Names are UPPERCASE (e.g. ``GMAIL``). The matching toolkit is the lowercase form. Inside a run the agent invokes them with the provider's verb: ``composio gmail <action>`` or ``pipedream gmail <action>``. To connect one, call `upsert_integration`. Remote types return an ``oauth_url`` (status ``pending``) the user opens to finish the handshake, after which you poll the ``integrations`` row until ``data->composio->>connected_account_id`` (or the ``pipedream`` equivalent) is set. When a type is offered by more than one of the workspace's enabled providers, pass ``provider`` to pick one (`find_providers` names each entry's provider), and Pipedream also requires ``profile_id``. Remote credentials are OAuth-managed, so never pass them inline. A row's stamped account identity (``email``/``identifier``) is what the last connection handshake reported, and a later re-grant can leave it stale. Trust it for ordinary calls. When you are about to arm unattended work (a trigger, a scheduled agent) on an existing connection and the stamp is missing, or the user's ask hinges on which account acts, name the account the stamp holds (or say the row carries none) and have the user confirm it before arming, reconnecting when it is wrong. Native types (MCP, CURSOR, HOLDED, PRESTASHOP) connect immediately: put their config in ``data`` and credentials per **Secrets and credentials** in `operations.md`. A database is not an integration: a POSTGRES, MYSQL, MONGODB, REDIS, SMTP, IMAP, AMQP, MQTT or LDAP connection is a secret the platform signs into on the agent's behalf (see **Secrets and credentials** in `operations.md`). An **MCP** integration is a connected remote MCP server, and its tool catalog is per-integration and discovered live, so list it with `list_toolkit_tools` passing the row's ``integration_id`` (a bare ``MCP`` name without one is rejected). An MCP server that signs users in over OAuth (no key or header to store) connects through `start_native_oauth_connection` instead of `upsert_integration`: mint a ``flow_id`` (any fresh UUID), pass ``workspace_id``, ``profile_id`` and a ``draft`` holding the integration you would otherwise upsert (``type`` ``MCP``, ``data.url`` the server), hand the user the returned URL, and poll `oauth_status` with the same ``flow_id`` until it answers ``completed`` with the ``integration_id`` it created. The row exists only once the grant lands, so a flow the user abandons leaves nothing behind. Reconnect an existing OAuth integration the same way, passing its ``integration_id`` in place of ``draft``. A server that hands out a pre-registered confidential client takes ``client_id`` and ``client_secret`` on the same call.
- **When a remote handshake fails.** The sign-in page belongs to the provider (Composio or Pipedream), and most Composio-managed types complete with nothing but the user's sign-in. Some services gate the provider's OAuth client on their own side: the service demands the app be installed or approved on the account first, usually by that service's admin, and the user sees the service's error during sign-in ("app not installed", "approval required"). Composio's toolkit page at ``docs.composio.dev/toolkits/<slug>`` documents the exact step, and the install link when one exists: read it and hand the user that step with its link, rather than reasoning the cause out from the error alone. A connect attempt rejected with "isn't available yet" means the platform's Composio project has no auth config for the type: that is platform-side setup, so say it needs enabling and reach for an alternative. Alternatives that always exist when a handshake stays stuck: the same type through another enabled provider (`find_providers` names each entry's provider), a credential the service issues directly (an API key or personal token, collected per **Secrets and credentials** in `operations.md`), or the agent working through the browser. Present a remedy only with its concrete step attached, and never park the work on an option the user cannot act on.
- **Assets** are resources VibeTasking provisions on the user's behalf (Twilio numbers, Supabase projects, mailboxes, hosted sites, proxy allocations). Same uppercase ↔ lowercase pattern. The agent calls them as platform toolkits, e.g. ``twilio <action>``. To provision a new one, call `quote_asset`: it returns ``credits`` (the recurring monthly price), ``due_now`` (what provisioning debits today, the part of that price left in the running subscription cycle), a ``preview`` of what will be provisioned, and a signed ``quote_id`` valid 10 minutes. Then `upsert_asset(type, workspace_id, params, accept_quote=<quote_id>)` confirms it. Provisioning runs synchronously and **debits ``due_now``** (auto-purchasing if the balance is short). Both calls need an ADMIN profile (OWNER for a STRIPE asset), the ``action:provision_assets`` scope on your key, and an active subscription (402 without one). The subscription holds the assets: when it ends they are released seven days later unless a plan is taken again, and an ``ASSET_RELEASE_SCHEDULED`` inbox row names the date. Existing provisioned assets live in the ``assets`` table (`query_data`). To **operate** one, see **Calling a toolkit tool directly vs. delegating** in `delegating.md` (Twilio/Email via `call_toolkit_tool` over the MCP or as their own commands in a run's sandbox, Supabase via `asset_proxy_read` and `asset_proxy_call`, Site via the `site_*` endpoints). A **STRIPE** asset (a connected Stripe account the workspace collects payments into) has its own endpoints: `get_stripe_status` and `stripe_onboarding_link` carry the account through Stripe's onboarding, `get_stripe_balance`, `get_stripe_payments`, `get_stripe_disputes` and `get_stripe_subscriptions` read it, and the catalog is managed with `get_stripe_catalog`, `create_stripe_product`, `create_stripe_price`, `create_stripe_payment_link` and their archive and deactivate counterparts, plus `create_stripe_refund` from a run. A **LINKEDIN** asset is readied with `linkedin_connect_link` (the hosted sign-in the user completes), and `linkedin_inboxes` lists the account's own inbox and the company pages it administers for `upsert_channel`'s ``mailbox_id``. **Regulated phone numbers.** `list_number_countries` marks the countries and number types whose purchase needs a regulatory bundle (the buyer's identity and address, filed with the carrier). Build one with `bundle_requirements` (what the country asks for), `create_bundle` (the draft with the end user and address), `add_bundle_document` (each supporting document), then `submit_bundle_for_review`, and the carrier answers within hours to days as a ``BUNDLE_UPDATED`` inbox row, and `list_bundles` shows the status. Only then does the number purchase go through. All of it needs an ADMIN profile, the bundles table's verbs on your key, and ``action:submit_bundles`` to send one for review.
- **Channels** are two-way messaging surfaces (WhatsApp, Telegram, SMS, email, Instagram, Messenger, Slack, LinkedIn, plus real-time voice calls). Incoming messages start or feed a run. The agent can reply through the same channel. Useful when building chatbots or human-in-the-loop touchpoints. For unattended automations a trigger is usually what you want instead. To connect one, check `channel_availability` for what the deployment supports. **TELEGRAM** connects via `upsert_channel` with a ``bot_token`` (from @BotFather). **SMS** via `upsert_channel` with the ``asset_id`` of a provisioned TWILIO asset (`list_numbers` shows provisionable numbers). **EMAIL** via `upsert_channel` with an EMAIL asset's ``asset_id``, or bring-your-own mailbox (``address`` plus ``smtp``/``imap`` credentials, verified before saving). A bring-your-own mailbox is reconfigured the same way on update (``id`` plus the field): ``smtp`` or ``imap`` with the password re-probes the login and rotates the stored password, a new IMAP host or account restarts the inbox cursor, ``poll_interval_seconds`` changes how often the inbox is read, and ``address`` the sender address. A mailbox connected over Google or Microsoft sign-in is reconnected from the app, its provider holds the login, and a provisioned mailbox has no credentials to change. **VOICE** via `upsert_channel` with a voice-capable TWILIO asset's ``asset_id`` plus a required ``agent_id`` (`channel_availability` says whether the deployment takes voice). The agent's voice, language and the rest are configured per channel afterwards, see **Voice agents** below. **LINKEDIN** via `upsert_channel` with the ``asset_id`` of a connected LINKEDIN asset (a LinkedIn account connected through the hosted sign-in wizard minted when the asset is provisioned), and pass ``mailbox_id`` (from `linkedin_inboxes`) to bind a company-page inbox instead: such channels answer as the page, reply-only. Connecting the account only readies the asset. Every type here works the same way: a channel exists only through its explicit connect call, and one connected without an ``agent_id`` keeps each contact's messages in their conversation, held for the workspace's people to answer from the app, with no agent run and no spend. Attaching an agent (`upsert_channel` with ``id`` plus ``agent_id``) hands it those conversations, and changing the agent moves them to the new one. On a channel with no agent, `start_run` with ``channel_id``, ``contact_id``, ``text`` and ``direct: true`` sends the contact a message from the team. **A channel serves exactly one agent** (``channels.agent_id``), and its toolkit binds only to that agent's runs: the conversation runs the channel opens, a run started on the agent with ``contact_id``, and a scheduled fire carrying one. Another agent's run never carries it, whatever its prompt names, and ``public`` on the channel row shares it with the workspace's members, never with other agents. An agent that has to message a contact on a channel it does not serve starts a run on the serving agent with ``contact_id`` and the instruction as ``text`` (see **Channel-attached agents** in `runs.md`), so a prompt written for that agent names `start_run`, never the channel's toolkit. Over the MCP, `call_toolkit_tool` with ``channel_id`` sends headless on any channel your key may read. Attaching the agent's first channel is refused while any of its cron triggers still carries no ``data.contact_id`` (see **Triggers** in `building.md`): a schedule on a channel agent addresses a named contact, so set one on each trigger, or drop the schedule, and retry the attach. **WHATSAPP**, **INSTAGRAM**, **MESSENGER**, and **SLACK** connect via a Meta/Slack signup popup, not via `upsert_channel`. Request the connection with a card: over the MCP, `send_message` to your own run, and from a run ``message_user``, in both cases with ``kind`` set to ``channel`` and ``types`` naming the channel type (e.g. ``["INSTAGRAM"]``). The card runs the signup, links the channel to the agent on completion, and shows the user where it lands. A Slack workspace already connected takes another channel on the same install (a signup naming an agent that already has one refreshes that channel instead). Each Slack channel answers the conversations ``config.slack.conversations`` claims, one claiming none answers every conversation no sibling claims, and two claiming the same conversation both answer it. Never paste a connect URL into the conversation (it expires within minutes and nothing tracks the outcome). `channel_connect_link` returns the raw ``connect_url`` for exactly one case: embedding the signup in a surface you built outside this conversation. **CUSTOM** channels are agent-operated surfaces you build yourself, see **Custom channels** below.
- **Connections on a channel agent.** A channel conversation has no owner, so ``allow_connections`` is off there unless the agent sets it, and the agent can then neither mint a connect link nor ask for an integration: a Gmail it lost stays lost for that contact. Set ``allow_connections: true`` on the agent (`upsert_agent` ``data``) when the contact is the person whose own accounts the agent works on, a personal assistant on WhatsApp or on a phone line: the agent then texts that contact a link that connects the account for their conversation. Leave it off when the contacts are the public, a support line or an outreach agent, since nobody there should connect anything to the workspace. On **VOICE** the link travels by text, so it needs a number that texts the caller: a number whose TWILIO asset lacks ``sms`` in ``data.capabilities`` (many local numbers outside North America are voice only) cannot send one, and a US or Canadian toll-free number texts a +1 caller only once its toll-free verification is approved.
- **A channel's own profile.** What contacts see on the channel is edited through `upsert_channel` with ``id`` plus ``profile``: on **WHATSAPP** the business profile (``about``, ``description``, ``address``, ``email``, ``vertical``, ``websites``), on **TELEGRAM** the bot's ``name``, ``description`` and ``short_description`` (optionally per ``language_code``). ``profile.photo_url`` replaces the picture from an https URL you can reach (a hosted image, or, over the MCP, a file you uploaded to a run and read back through `get_download_url`). Only the keys you pass change. A WhatsApp number still paired with the WhatsApp Business app refuses profile writes, since the app owns the profile. Nothing else on the channel takes a profile.
- **Slack conversation scope.** ``config.slack`` carries ``scope``: ``thread`` (each thread is its own conversation) or ``channel`` (the whole channel is one), and ``conversations``: the conversation ids (``C…``, ``G…``, ``D…``) or, on an organization install, team ids (``T…``) the channel claims, empty to answer every conversation no sibling on the same Slack workspace claims.
- **WhatsApp numbers.** The connection card first asks where the number comes from, and a user without a number to spare still gets one there. A **platform number** is a voice-capable TWILIO number the workspace already holds, or a new one bought inside the card: the platform answers Meta's verification call on it and shows the user the code, so no phone or SIM is involved. A number a VOICE channel answers is not offered, since its voice agent would take that call. The user's **own number** goes through Meta's signup popup, which offers two paths and the user picks inside it: a new Cloud API number, or **coexistence**, where a number already running the WhatsApp Business app stays in that app on the phone while the platform reads and sends on the same line. A number on the WhatsApp Business app therefore needs no second number, and the chats already on the phone arrive once, right after onboarding. Coexistence keeps the business profile (name, description, photo) owned by the app, so it is edited there, and voice calling needs a Cloud API number. The owner replying from the phone pauses the agent on that conversation, and ``operator_timeout`` (an `upsert_channel` ``config`` key, seconds of owner silence before the agent takes the conversation back) is what resumes it, so set it whenever the owner keeps answering from the phone. The app's own greeting and away messages count as the owner replying, so they are better switched off. A number on the consumer WhatsApp app is the one that needs a change: move it to the WhatsApp Business app first, or connect a separate number.

## Voice agents

A **VOICE** channel is an AI agent answering (and placing) phone calls on a Twilio number. A speech model talks with the caller, and everything it cannot answer itself it hands to the contact's conversation run, which is the channel's agent taking a turn as on any message: its own model, instructions and tools, so there is no model, reasoning or tool selection on the channel. How the call sounds is configured per channel:

- `voice_settings` returns the channel's current settings plus the catalog to configure it from: ``voices`` to pick from (each with a description and a sample), ``languages`` (the default the channel starts in), ``defaults`` (the voice and the duration cap that apply when the channel sets none) and ``base`` (the per-minute cost in credits).
- `configure_voice` changes any of it: ``prompt`` (the speaking instructions: identity, tone, pronunciation and required wording, including the line the call opens with, an explicit null or a blank string clears it), ``language`` (the spoken language the agent starts every call in, the caller may switch it), ``voice`` (an entry from the catalog's ``voices``, passed verbatim), ``recording``, ``summary``, ``max_seconds`` (call duration cap, an explicit null restores the platform's), ``handoff_number`` (human transfer target, an explicit null clears it), ``handoffs`` (named transfer destinations) and ``transfer_summary`` (brief the person receiving a transfer, on by default). Only the keys you pass change. Business procedures belong in the agent and preset prompts, which the conversation run answers the call with. Changes apply from the next call.

**Calling on a WhatsApp number.** Voice is a capability of the existing WHATSAPP channel, not a second channel: the same number that texts also takes and places calls, and each call lands on the contact's conversation. Switch it on with `upsert_channel` (``id`` plus ``voice`` carrying the same keys `configure_voice` takes, an empty object is enough) or with `configure_voice` on the channel itself, and read the option catalog with `voice_settings` as for a VOICE channel, and `upsert_channel` with ``voice`` as an explicit null switches it off and tears the wiring down. It needs a Cloud API number (a coexistence number is refused) and an agent attached, and a refused enable rolls back so the row never claims a capability Meta denied.

**Placing a call.** `start_run` on the voice channel's agent with ``contact_id`` (the E.164 number to dial) places the call, and ``text`` becomes the call's briefing. The outcome (transcript, summary) lands on the returned conversation run: poll `get_run_status` to read it. Inside the channel's own runs the agent carries the ``voice`` toolkit: ``say`` speaks to the caller while a call is live, ``send_sms`` texts them a link from the same number, ``place_call`` and ``get_call`` dial and read back. Those tools exist only there, bound to the VOICE channel at run time, so a toolkit listing outside a run never shows them: from here, `start_run` is the call surface. A voice-enabled WHATSAPP channel places calls the same way with ``call: true``. A schedule never fires a VOICE channel, so a trigger cannot place calls.

## Custom channels

A **CUSTOM** channel turns a messaging surface the platform has no built-in support for (a community forum, a marketplace inbox) into a first-class channel: one conversation run per contact, operator takeover, the standard transcript. The transport is agent-operated. You define it with agents and prompts, and the platform contributes identity, contact validation, idempotent injection, and delivery bookkeeping.

Create one with `upsert_channel`: ``type: "CUSTOM"``, a required ``agent_id`` (the conversation agent), and a ``custom`` descriptor carrying ``name``, an optional emoji ``icon``, ``contact_id_pattern``, an optional ``contact_id_hint``, and a required ``router_agent_id`` (a dedicated agent, different from the conversation agent, that delivers the channel, see **The router agent** below). The pattern is the channel's contact contract: pick one canonical id form (the platform's stable conversation or user id, never a display name) and accept only it, since the contact id keys "one run per contact" and two spellings of one contact fork the conversation into parallel runs. Write the chosen form into every prompt that touches the channel.

**Inbound.** Whatever observes the external platform (a cron-fired agent, a webhook trigger, a script) injects each new message with `start_run` (or, from an ownerless run, the built-in ``start_run``): the conversation ``agent_id``, the ``contact_id``, the message ``text``, plus ``contact_name`` and ``external_id`` (the message's id on the external platform). The platform finds or creates that contact's run, appends the message, and dispatches it. While the channel has no agent, the router injects with ``channel_id`` in place of ``agent_id``, and the message waits in the contact's conversation for the workspace's people. ``external_id`` makes injection idempotent: re-injecting the same message returns ``deduplicated: true`` and changes nothing, so always pass it when the platform provides an id.

**Outbound** rides the router: conversation runs call the ``custom`` toolkit's ``send_message``, which queues the reply and wakes the router. Operator messages queue the same way, so takeover works. For an API-backed transport (a vendor that offers a REST API) the router's transport calls are API calls instead of browser driving, and the shape is the same.

**The router agent** owns transport and nothing else: it delivers, fetches, and injects, and never composes replies. Starting it is a wake: runs are serialized per channel, so a start that lands while another router run is executing joins it instead of starting a second one (``skipped: true``, and ``run_id`` names the run already doing the work). A fresh wake (``skipped: false``) started by a run notifies its starter when it settles, like any delegated start (``watch: false`` opts out). A joined run never notifies the joiner, so poll ``get_run_status`` on the returned ``run_id`` when you need its outcome. Give it a cron trigger at the cadence the user wants (the dominant cost dial) and a prompt that instructs, in order:

1. Drain the queue with the ``custom`` toolkit's CLI: ``custom pending_messages --json '{}'`` lists the pending replies, deliver each through the transport, then ``custom mark_delivered --json '{"message_id": "…", "external_id": "…"}'`` with the id the platform returned. When newer inbound from the same contact arrived after a pending reply's ``created_at``, the reply is stale: skip the send and mark it delivered with no external id, and the conversation run will answer the newer message instead. **Spell the ``custom …`` commands out in the router prompt.** A router agent has no channel attached to it (the channel points at the *conversation* agent), so the toolkit is reachable but never advertised as ready-to-use: a prompt that only names the bare tools leaves the agent hunting for a surface it can't discover.
2. Fetch new inbound from the external platform and inject each message per **Inbound** above, with ``external_id`` always set.
3. Stop when there is nothing left to deliver or ingest. On a transport auth failure (a login wall, an expired session), stop and report instead of retrying.

For a browser transport, set ``browser_storage: true`` and ``browser_agent_storage: true`` on the router agent: the browser session (cookies, storage) is stashed at the agent scope when the browser stops, so every router run opens the browser already logged in. The user logs in once by hand, through a run with the live browser handed off (``message_user`` with ``action`` ``browser``).
