## Integrations, assets, channels

- **Integrations** are OAuth connections to third-party services via Composio or Pipedream (the integration's ``provider``). Names are UPPERCASE (e.g. ``GMAIL``). The matching toolkit is the lowercase form. Inside a run the agent invokes them with the provider's verb: ``composio gmail <action>`` or ``pipedream gmail <action>``. To connect one, `create_connection` with ``type`` ``COMPOSIO`` or ``PIPEDREAM``, the app as ``toolkit`` (as `list_providers` names it) and, to link the account to an agent as it lands, ``agent_id``: hand the user the ``url`` it answers, then read `get_connection` until it is ``completed`` and names the ``integration_id`` it created, or ``failed`` with why. Pass ``integration_id`` instead to replace a broken account in place, its links kept. `list_providers` names each entry's provider when a type is offered by more than one of the workspace's enabled providers. Remote credentials are OAuth-managed, so never pass them inline. An integration's ``account`` is what the last connection handshake reported, and a later re-grant can leave it stale. Trust it for ordinary calls. When you are about to arm unattended work (a trigger, a scheduled agent) on an existing connection and the account is missing, or the user's ask hinges on which account acts, name the account it holds (or say it carries none) and have the user confirm it before arming, reconnecting when it is wrong. Native types (MCP, CURSOR, HOLDED, PRESTASHOP) connect immediately through `create_integration` with their settings in ``config`` and credentials per **Secrets and credentials** in `operations.md`. A database is not an integration: a POSTGRES, MYSQL, MONGODB, REDIS, SMTP, IMAP, AMQP, MQTT, LDAP or SSH connection is a secret the platform signs into on the agent's behalf (see **Secrets and credentials** in `operations.md`). An **MCP** integration is a connected remote MCP server, and its tool catalog is per-integration and discovered live, so list it with `list_toolkit_tools` passing its ``integration_id`` (a bare ``MCP`` name without one is rejected). An MCP server that signs users in over OAuth (no key or header to store) connects through `create_connection` with ``type`` ``OAUTH`` and a ``config`` holding the integration you would otherwise create (the server's ``url``): hand the user the answered ``url`` and read `get_connection` until it is ``completed`` with the ``integration_id`` it created. The integration exists only once the grant lands, so a flow the user abandons leaves nothing behind. Reconnect an existing OAuth integration the same way, passing its ``integration_id`` in place of ``config``. A server that hands out a pre-registered confidential client takes ``client_id`` and ``client_secret`` on the same call.
- **When a remote handshake fails.** The sign-in page belongs to the provider (Composio or Pipedream), and most Composio-managed types complete with nothing but the user's sign-in. Some services gate the provider's OAuth client on their own side: the service demands the app be installed or approved on the account first, usually by that service's admin, and the user sees the service's error during sign-in ("app not installed", "approval required"). Composio's toolkit page at ``docs.composio.dev/toolkits/<slug>`` documents the exact step, and the install link when one exists: read it and hand the user that step with its link, rather than reasoning the cause out from the error alone. A connect attempt rejected with "isn't available yet" means the platform's Composio project has no auth config for the type: that is platform-side setup, so say it needs enabling and reach for an alternative. Alternatives that always exist when a handshake stays stuck: the same type through another enabled provider (`list_providers` names each entry's provider), a credential the service issues directly (an API key or personal token, collected per **Secrets and credentials** in `operations.md`), or the agent working through the browser. Present a remedy only with its concrete step attached, and never park the work on an option the user cannot act on.
- **Assets** are resources VibeTasking provisions on the user's behalf (Twilio numbers, Supabase projects, mailboxes, hosted sites, Stripe accounts, proxy allocations, LinkedIn seats). Same uppercase ↔ lowercase pattern. The agent calls them as platform toolkits, e.g. ``twilio <action>``. `list_assets` lists the workspace's provisioned assets. To **operate** one, see **Calling a toolkit tool directly vs. delegating** in `delegating.md` (Twilio/Email via `call_toolkit_tool` over the MCP or as their own commands in a run's sandbox, Supabase via `read_asset_api` and `call_asset_api`, Site via its site operations). A **STRIPE** asset (a connected Stripe account the workspace collects payments into) has its own operations: `get_stripe_account` and `create_stripe_onboarding_link` carry the account through Stripe's onboarding, `get_stripe_balance`, `list_stripe_payments`, `list_stripe_disputes` and `list_stripe_subscriptions` read it, and the catalog is managed with `list_stripe_products`, `create_stripe_product`, `create_stripe_price`, `create_stripe_payment_link` and their archive and deactivate counterparts, plus `create_stripe_refund` from a run. A **LINKEDIN** asset is readied with `create_connection` of ``type`` ``LINKEDIN`` and its ``asset_id`` (the hosted sign-in the user completes), and `list_linkedin_inboxes` lists the account's own inbox and the company pages it administers for `create_channel`'s ``mailbox``. **Regulated phone numbers.** `list_number_countries` marks the countries and number types whose purchase needs a regulatory bundle (the buyer's identity and address, filed with the carrier). Build one with `list_bundle_requirements` (what the country asks for), `create_bundle` (the draft with the end user and address), `add_bundle_document` (each supporting document), then `submit_bundle`, and the carrier answers within hours to days as a ``BUNDLE_UPDATED`` activity, and `list_bundles` shows the status. Only then does the number purchase go through. All of it needs an ADMIN profile, the bundles scopes on your key, and ``action:submit_bundles`` to send one for review.
- **Free and priced assets.** A SITE, an EMAIL mailbox and a STRIPE account cost nothing to hold, so `create_asset` takes them with ``type`` and ``params`` alone, on any plan, and the free plan holds one site and one mailbox (402 past that, naming the limit). A TWILIO number, a SUPABASE database, a PROXY allocation and a LINKEDIN seat are priced: call `quote_asset` first. It returns ``credits`` (the recurring monthly price), ``due_now`` (what provisioning debits today, the part of that price left in the running subscription cycle), a ``preview`` of what will be provisioned, and a signed ``quote`` valid 10 minutes. Then `create_asset` with the same ``type`` and ``params`` and that ``quote`` confirms it. Provisioning runs synchronously and **debits ``due_now``** (auto-purchasing if the balance is short), and a priced type needs an active subscription (402 without one). A priced create needs an ADMIN profile, a free one any member who manages credentials and channels, and every create the ``action:provision_assets`` scope on your key. The subscription holds the priced assets, and any free one past the free plan's room: when it ends they are released seven days later unless a plan is taken again, and an ``ASSET_RELEASE_SCHEDULED`` activity names the date. A phantom workspace, a demo its visitor has not claimed yet, creates no real asset (403).
- **Channels** are two-way messaging surfaces (WhatsApp, Telegram, SMS, email, Instagram, Messenger, Slack, Microsoft Teams, TikTok, LinkedIn, plus real-time voice calls). Incoming messages start or feed a run. The agent can reply through the same channel. Useful when building chatbots or human-in-the-loop touchpoints. For unattended automations a trigger is usually what you want instead. To connect one, check `list_channel_types` for what the deployment supports. **TELEGRAM** connects via `create_channel` with a ``bot_token`` (from @BotFather). **SMS** via `create_channel` with the ``asset_id`` of a provisioned TWILIO asset (`list_numbers` shows provisionable numbers). **EMAIL** via `create_channel` with an EMAIL asset's ``asset_id``, or bring-your-own mailbox (``address`` plus ``smtp``/``imap`` credentials, verified before saving). A bring-your-own mailbox is reconfigured with `update_channel`: ``smtp`` or ``imap`` with the password re-probes the login and rotates the stored password, a new IMAP host or account restarts the inbox cursor, ``poll_interval_seconds`` changes how often the inbox is read, and ``address`` the sender address. A mailbox connected over Google or Microsoft sign-in is reconnected from the app, its provider holds the login, and a provisioned mailbox has no credentials to change. **VOICE** via `create_channel` with a voice-capable TWILIO asset's ``asset_id`` plus a required ``agent_id`` (`list_channel_types` says whether the deployment takes voice). In Spain, a voice channel that places sales or telemarketing calls takes a NATIONAL number in the ``COMMERCIAL`` range (`list_numbers` names it in ``range``), which only places calls and which nobody can call, and one that takes calls or serves existing customers takes a LOCAL number. The agent's voice, language and the rest are configured per channel afterwards, see **Voice agents** below. **LINKEDIN** via `create_channel` with the ``asset_id`` of a connected LINKEDIN asset, and pass ``mailbox`` (from `list_linkedin_inboxes`) to bind a company-page inbox instead: such channels answer as the page, reply-only. Connecting the account only readies the asset. Every type here works the same way: a channel exists only through its explicit connect call, and one connected without an ``agent_id`` keeps each contact's messages in their conversation, held for the workspace's people to answer from the app, with no agent run and no spend. Attaching an agent (`update_channel` with ``agent_id``) hands it those conversations, and changing the agent moves them to the new one. On a channel with no agent, `start_conversation` with ``contact``, ``text`` and ``send: direct`` sends the contact a message from the team. **A channel serves exactly one agent** (its ``agent_id``), and its toolkit binds only to that agent's runs: the conversation runs the channel opens, a conversation you start on it, and a scheduled fire carrying a contact. Another agent's run never carries it, whatever its prompt names, and ``public`` on the channel shares it with the workspace's members, never with other agents. An agent that has to message a contact on a channel it does not serve starts the conversation on that channel with ``contact`` and the instruction as ``text`` (see **Channel-attached agents** in `runs.md`), so a prompt written for that agent names `start_conversation`, never the channel's toolkit. Over the MCP, `call_toolkit_tool` with ``channel_id`` sends headless on any channel your key may read. Attaching the agent's first channel is refused while any of its cron triggers still carries no ``contact`` in its ``config`` (see **Triggers** in `building.md`): a schedule on a channel agent addresses a named contact, so set one on each trigger, or drop the schedule, and retry the attach. **WHATSAPP**, **INSTAGRAM**, **MESSENGER**, **SLACK**, **TEAMS** and **TIKTOK** connect via a signup popup, not via `create_channel`. Request the connection with a card: over the MCP, `send_message` to your own run, and from a run ``message_user``, in both cases with ``kind`` set to ``channel`` and ``types`` naming the channel type (e.g. ``["INSTAGRAM"]``). TEAMS needs an administrator of the Microsoft 365 organization to approve the app, then the app is added in Teams. TIKTOK takes a business account: its comments become conversations, and its direct messages too where TikTok allows them, always answered within TikTok's reply window, never started. The card runs the signup, links the channel to the agent on completion, and shows the user where it lands. A Slack workspace already connected takes another channel on the same install (a signup naming an agent that already has one refreshes that channel instead), and a Teams organization the same way. Each Slack channel answers the conversations its ``settings.slack.conversations`` claims (a Teams channel its ``settings.teams.conversations``), one claiming none answers every conversation no sibling claims, and two claiming the same conversation both answer it. Never paste a connect URL into the conversation (it expires within minutes and nothing tracks the outcome). `create_connection` with the channel's type answers the raw ``url`` for exactly one case: embedding the signup in a surface you built outside this conversation. **CUSTOM** channels are agent-operated surfaces you build yourself, see **Custom channels** below.
- **Connections on a channel agent.** A channel conversation has no owner, so ``allow_connections`` is off there unless the agent sets it, and the agent can then neither mint a connect link nor ask for an integration: a Gmail it lost stays lost for that contact. Set ``allow_connections: true`` in the agent's ``config`` (`update_agent`) when the contact is the person whose own accounts the agent works on, a personal assistant on WhatsApp or on a phone line: the agent then texts that contact a link that connects the account for their conversation. Leave it off when the contacts are the public, a support line or an outreach agent, since nobody there should connect anything to the workspace. On **VOICE** the link travels by text, so it needs a number that texts the caller: a number whose TWILIO asset lacks ``sms`` in its ``details.capabilities`` (many local numbers outside North America are voice only) cannot send one, and a US or Canadian toll-free number texts a +1 caller only once its toll-free verification is approved.
- **A channel's own profile.** What contacts see on the channel is edited through `update_channel` with ``profile``: on **WHATSAPP** the business profile (``about``, ``description``, ``address``, ``email``, ``vertical``, ``websites``), on **TELEGRAM** the bot's ``name``, ``description`` and ``short_description`` (optionally per ``language_code``). ``profile.photo_url`` replaces the picture from an https URL you can reach (a hosted image, or, over the MCP, a file you wrote to a disk and read back through `get_file`'s link). Only the keys you pass change. A WhatsApp number still paired with the WhatsApp Business app refuses profile writes, since the app owns the profile. Nothing else on the channel takes a profile.
- **Slack conversation scope.** ``settings.slack`` carries ``scope``: ``thread`` (each thread is its own conversation) or ``channel`` (the whole channel is one), and ``conversations``: the conversation ids (``C…``, ``G…``, ``D…``) or, on an organization install, team ids (``T…``) the channel claims, empty to answer every conversation no sibling on the same Slack workspace claims.
- **WhatsApp numbers.** The connection card first asks where the number comes from, and a user without a number to spare still gets one there. A **platform number** is a voice-capable TWILIO number the workspace already holds, or a new one bought inside the card: the platform answers Meta's verification call on it and shows the user the code, so no phone or SIM is involved. A number a VOICE channel answers is not offered, since its voice agent would take that call. The user's **own number** goes through Meta's signup popup, which offers two paths and the user picks inside it: a new Cloud API number, or **coexistence**, where a number already running the WhatsApp Business app stays in that app on the phone while the platform reads and sends on the same line. A number on the WhatsApp Business app therefore needs no second number, and the chats already on the phone arrive once, right after onboarding. Coexistence keeps the business profile (name, description, photo) owned by the app, so it is edited there, and voice calling needs a Cloud API number. The owner replying from the phone pauses the agent on that conversation, and ``operator_timeout`` (a channel ``settings`` key, seconds of owner silence before the agent takes the conversation back) is what resumes it, so set it whenever the owner keeps answering from the phone. The app's own greeting and away messages count as the owner replying, so they are better switched off. A number on the consumer WhatsApp app is the one that needs a change: move it to the WhatsApp Business app first, or connect a separate number.
- **WhatsApp message templates.** A WhatsApp channel reaches a contact who has not written in the last 24 hours, or opens a conversation, only with a template Meta approved. `list_channel_templates` lists the business account's templates with their ``status`` (``APPROVED``, ``PENDING``, ``REJECTED``) and `rejected_reason`, `create_channel_template` submits one (``name``, ``language``, ``category`` and its ``components``, each variable a number in double curly braces) for Meta's review, which usually takes minutes to hours, `update_channel_template` changes an approved one's category or components, and `delete_channel_template` removes one, every language or the one ``template`` names. `start_conversation` with ``whatsapp_template`` sends an approved one. These are the account's own blueprints, unrelated to agents (see **Not WhatsApp message templates** in `building.md`).

## Voice agents

A **VOICE** channel is an AI agent answering (and placing) phone calls on a Twilio number. A voice agent talks with the caller, and everything it cannot answer itself it hands to the contact's conversation run, which is the channel's agent taking a turn as on any message: its own model, instructions and tools, so there is no model, reasoning or tool selection on the channel. How the call sounds is configured per channel:

- `get_channel` answers the channel's call settings under ``settings.voice``, and `list_voices` the voices to pick from, each with its name (``label``), gender, ``accent``, ``locale``, ``age`` and ``style`` (its character in one word) where the provider says, whether it is the language's default (``default``, listed first: the voice a channel that picks none speaks with, the platform's pick for the language, so the one to offer first), whether ElevenLabs verified it for the language on the synthesis model (``verified``, which only ranks the voices after the default, the verified first), a description and a sample: pass ``provider`` for a provider's voices (OpenAI Live's when you pass none), ``gender`` for one gender's, and on ElevenLabs ``language`` for the call's and ``style`` for one character's (``calm``, ``casual``, ``confident``, ``pleasant``, ``professional``, ``upbeat``, ``gentle``, ``formal``). On ElevenLabs also pass the channel's ``synthesis`` from its ``settings.voice``, the model ``verified`` is judged on. An ``accent`` of null is the language's standard one, so a caller asking for Spain's Spanish wants ``spanish (castilian)`` or the locale ``es-ES``.
- Who speaks on the calls is the channel agent's call configuration, ``models.call`` in its ``config`` (see **Models** in `configuration.md`), never a channel setting: an entry for OpenAI Live (model ``openai:gpt-live-1``), ElevenLabs (``elevenlabs:agents``), each on one of the platform's accounts `get_purposes` lists, or the platform's own voice loop (``loop:voice`` on the ``voice-loop`` provider), the first that runs speaking and the rest taking a call it cannot. Both vendors hand the conversation to the agent the same way. With no ``models.call`` the agent speaks on the workspace's configuration, else on the platform's.
- `update_channel` with ``settings.voice`` changes any of it, merged key by key: ``prompt`` (the speaking instructions: identity, tone, pace, pronunciation and required wording, including the line the call opens with, an explicit null or a blank string clears it), ``language`` (the spoken language the agent starts every call in, the caller may switch it), ``voice`` (an entry from the catalog's ``voices``, passed verbatim: the channel keeps one voice per provider, read back under ``settings.voice.voices``, and a call speaks the one of the provider it runs on, else that provider's default), ``recording``, ``summary``, ``max_seconds`` (call duration cap, an explicit null restores the platform's), ``handoff_number`` (human transfer target, an explicit null clears it), ``handoffs`` (named transfer destinations), ``transfer_summary`` (brief the person receiving a transfer, on by default), ``voicemail_detection`` (phone channels: ``off``, the default, connects the caller to whatever answers a transfer, ``manual`` asks whoever answers to press a key first and ``automatic`` listens to how the line answers, and either hangs up on a voicemail and hands the caller back to the agent, so it can offer a callback or book a slot, ``manual`` being the sure one and ``automatic`` the one that asks nothing of the person), ``transfer_timeout`` (phone channels: seconds a transfer rings before the caller goes back to the agent, an explicit null restores the platform's), ``skip_voicemail`` (phone channels: hang up a call the agent places when a voicemail answers it, which then ends as ``voicemail`` so it can be tried again later, off by default, and it can take a person who answers with a long greeting for a voicemail) and ``preconnect`` (phone channels: connect the agent while an outbound call rings so it is on the line from the moment the person picks up, its minutes billed from the first ring whether or not the call is answered, on by default). Only the keys you pass change, so on a configured channel pass only the ones the user asked to change: a setting you think the line needs (its recording, say) is a suggestion to make, never a write. Changes apply from the next call.

**What goes in the speaking instructions and what in the agent.** The speaking instructions reach the voice alone, and the conversation run never sees them. The voice also reads the agent's prompt, without the agent's own tools and procedures, written down for it automatically whenever the prompt changes (the app shows it as "What calls know"). So what the business is and offers, its places, hours, prices, contacts and policies, and every limit on what callers are told go in the agent's prompt, where both the voice and the conversation run read them. The speaking instructions keep identity, tone, pace, pronunciation and required wording, and procedures belong in the agent and preset prompts. When a user wants the voice faster or slower, add that to the speaking instructions ("Speak slowly and calmly.").

**Choosing the provider and the voice with the user.** Before you set either, ask who the calls are for and offer the choice. OpenAI Live feels quicker and sharper in the conversation itself, while its voices speak Spanish without a native regional accent: suggest it for calls inside the business. ElevenLabs voices sound like a person from the region, accent included: suggest it when the people on the line should not feel they talk to a machine. Set the one they pick as the first entry of the agent's ``models.call``. Then ask whether they want a woman's or a man's voice and what character it should have, list that provider's voices with `list_voices` narrowed by ``gender`` and, on ElevenLabs, ``style``, and offer two or three with their samples, the default first when it matches, naming each one's accent. Set the one they pick as the channel's ``voice``. A provider change the user asks for without naming a voice speaks the voice the channel keeps for the new provider, else its default: pass no ``voice``.

**Calling on a WhatsApp number.** Voice is a capability of the existing WHATSAPP channel, not a second channel: the same number that texts also takes and places calls, and each call lands on the contact's conversation. Switch it on with `update_channel` and ``settings.voice`` (an empty object is enough), read the voices with `list_voices` as for a VOICE channel, and ``settings.voice`` as an explicit null switches it off and tears the wiring down. It needs a Cloud API number (a coexistence number is refused) and an agent attached, and a refused enable rolls back so the row never claims a capability Meta denied.

**The shared test line.** A workspace with no number of its own still calls out: `create_channel` with ``type`` ``VOICE``, its ``agent_id`` and ``shared`` true in place of ``asset_id`` puts the channel on the platform's shared test line, on any plan, with no number to buy, and beside numbers of the workspace's own. Its numbers are every channel's, so the channel places calls and takes none and sends no texts. It speaks on any provider a number of the workspace's own does, ElevenLabs included. It calls any number, and each call costs credits like a call from a number of the workspace's own. A demo workspace takes it once its visitor claims it. `list_channel_types` names ``shared`` among the VOICE ``lines`` wherever it is set up.

**Placing a call.** `place_call` on the voice channel with ``contact`` (the E.164 number to dial) places the call, and ``objective`` becomes the call's briefing. As on any phone call, whoever picks up speaks first: the agent opens in reply to their greeting, and checks with a short hello when they stay silent. The outcome (transcript, summary) lands on the conversation run it names: read it with `get_run`, and the call itself with `get_call` on the ``call_id`` it answers: its status while it rings or runs, then its duration, ``summary`` and the ``recording_path`` `get_run_file` reads on that run. `list_calls` lists a workspace's calls, ``run_id`` narrowing it to one conversation's. Inside the channel's own runs the agent carries the ``voice`` toolkit: ``say`` speaks to the caller while a call is live, ``send_sms`` texts them a link from the same number, ``place_call`` and ``get_call`` dial and read back. Those tools exist only there, bound to the VOICE channel at run time, so a toolkit listing outside a run never shows them: from here, `place_call` is the call surface. When it is not among your tools, this surface places no calls, and neither do the runs you start or continue from it. A voice-enabled WHATSAPP channel places calls the same way, and a contact who has not allowed calls is asked first. A schedule never fires a VOICE channel, so a trigger cannot place calls. A call back the caller asks for needs no trigger: the conversation run agrees on when, ends the call, parks a message for itself at that time and places the call when it arrives.

## Custom channels

A **CUSTOM** channel turns a messaging surface the platform has no built-in support for (a community forum, a marketplace inbox, a chat window on the user's own site) into a first-class channel: one conversation run per contact, operator takeover, the standard transcript. The transport is either agent-operated, defined with a router agent and its prompt, or the user's own integration calling the API. The platform contributes identity, contact validation, idempotent injection, and delivery bookkeeping.

Create one with `create_channel`: ``type: "CUSTOM"``, an optional ``agent_id`` (the conversation agent, left out when the workspace's people answer every conversation themselves), and a ``custom`` descriptor carrying ``name``, an optional emoji ``icon``, ``contact_id_pattern``, an optional ``contact_id_hint``, and an optional ``router_agent_id`` (a dedicated agent, different from the conversation agent, that delivers the channel, see **The router agent** below, left out when the user's own integration delivers it, see **Delivered by the user's integration** below). The pattern is the channel's contact contract: pick one canonical id form (the platform's stable conversation or user id, never a display name) and accept only it, since the contact id keys "one run per contact" and two spellings of one contact fork the conversation into parallel runs. Write the chosen form into every prompt that touches the channel.

**Inbound.** Whatever observes the external platform (a cron-fired agent, a webhook trigger, a script) injects each new message with `start_conversation` on the channel (from an ownerless run, the built-in ``platform start_conversation`` of the same name): the ``contact``, the message ``text``, plus ``contact_name`` and ``external_ref`` (the message's id on the external platform). The platform finds or creates that contact's run, appends the message, and dispatches it. While the channel has no agent, the message waits in the contact's conversation for the workspace's people. ``external_ref`` makes injection idempotent: re-injecting the same message changes nothing and answers the same conversation, so always pass it when the platform provides an id.

**Outbound** rides the router: conversation runs call the ``custom`` toolkit's ``send_message``, which queues the reply and wakes the router. Operator messages queue the same way, so takeover works. For an API-backed transport (a vendor that offers a REST API) the router's transport calls are API calls instead of browser driving, and the shape is the same.

**Delivered by the user's integration.** A channel with no ``router_agent_id`` is delivered by code the user runs: it injects contacts' messages with `start_conversation` and reads the replies, which queue the same way, from `list_messages` on the conversation or the ``MESSAGE_INSERTED`` webhook. For a chat window on their site, their server mints a token per signed in visitor with `create_conversation_token` (the channel, the visitor's id on their site as ``contact``, and ``contact_name``), never for an id the browser chose, and the page sends it as ``Authorization: Bearer <token>`` to `list_conversation_messages` (polled with the last ``cursor`` as ``after``), `send_conversation_message` (text and files, with a new ``external_ref`` per message), `acknowledge_conversation` (with the newest message on screen as ``through``, so each reply's ``read`` holds on every device) and `get_conversation_file`. The token works for a day, so the server mints one each time the page opens.

**The router agent** owns transport and nothing else: it delivers, fetches, and injects, and never composes replies. Starting it is a wake: runs are serialized per channel, so a `create_run` that lands while another router run is executing joins it instead of starting a second one, and answers the run already doing the work. A fresh wake started by a run notifies its starter when it settles, like any delegated start (``watch: false`` opts out). A joined run never notifies the joiner, so read `get_run` on the answered run when you need its outcome. Give it a cron trigger at the cadence the user wants (the dominant cost dial) and a prompt that instructs, in order:

1. Drain the queue with the ``custom`` toolkit's CLI: ``custom pending_messages --json '{}'`` lists the pending replies, deliver each through the transport, then ``custom mark_delivered --json '{"message_id": "…", "external_ref": "…"}'`` with the id the platform returned. When newer inbound from the same contact arrived after a pending reply's ``created_at``, the reply is stale: skip the send and mark it delivered with no external id, and the conversation run will answer the newer message instead. **Spell the ``custom …`` commands out in the router prompt.** A router agent has no channel attached to it (the channel points at the *conversation* agent), so the toolkit is reachable but never advertised as ready-to-use: a prompt that only names the bare tools leaves the agent hunting for a surface it can't discover.
2. Fetch new inbound from the external platform and inject each message per **Inbound** above, with ``external_ref`` always set.
3. Stop when there is nothing left to deliver or ingest. On a transport auth failure (a login wall, an expired session), stop and report instead of retrying.

For a browser transport, set ``browser_storage: true`` and ``browser_agent_storage: true`` on the router agent: the browser session (cookies, storage) is stashed at the agent scope when the browser stops, so every router run opens the browser already logged in. The user logs in once by hand, through a run with the live browser handed off (``message_user`` with ``action`` ``browser``).
